# 「全部邮件」数据范围查证（只读，未改任何代码）

> 查证日期：2026-11-05
> 范围：`mail-vue`（网页版）、`mail-worker`（服务端）、`otsmail-android`（客户端）
> 本轮**未改服务端代码、未改客户端请求参数与数据范围**，所有结论来自静态阅读。

## 0. 一句话结论

**网页版能看到全站邮件**：入口是侧边栏「所有账户」→ 页面 `/all-email` → 接口 `GET /allEmail/list`。
这个接口**完全没有 `user_id` 过滤**，返回所有域名下所有用户的邮件；门槛只有一个权限键 `all-email:query`（或系统管理员 `user.type === 0`）。
客户端现在用的 `/email/list?...&allReceive=1` **不是全站**，它只展开到「当前登录用户名下的多个 account」。

## 1. 三层定义与现状表

| 层级 | 定义 | 现有接口 / 参数 | 实际返回范围 | 代码位置 |
|---|---|---|---|---|
| ① 当前账户 | 用户当前选中的 1 个邮箱 | `GET /email/list?accountId=N&allReceive=0` | 该 account 的邮件 | `mail-worker/src/service/email-service.js:144-151` |
| ② 该用户的所有邮箱 | 一个 `user` 名下的多个 `account` | `GET /email/list?accountId=0&allReceive=1` | 仅 `email.user_id = 当前 userId` 的邮件 | `email-service.js:144-151`（`allReceive ? eq(1,1) : ...` + `eq(email.userId, userId)`） |
| ③ 全站所有邮箱 | 所有域名下所有 `account` | `GET /allEmail/list` | **全站**（无 `user_id`、无 `account.is_del` 过滤） | `email-service.js:1011-1139`；守卫 `security.js:96` |
| 客户端「全部邮件」页 | 管理页，走 ② | `GET /email/list?size=20&page=N&allReceive=1&timeSort=0` | **②，不是③** | `app/src/main/java/com/otscup/otsmail/data/Api.kt:436`；调用方 `ui/AdminScreens.kt:199-203` |
| 网页版「所有账户」 | 走 ③ | `GET /allEmail/list?emailId&size&page&category&timeSort&type&...` | **③** | `mail-vue/src/views/all-email/index.vue:300-302`；`src/request/all-email.js:3-5` |

差异一句话：**网页版「所有账户」= 全站；客户端同名页面 = 当前用户全部邮箱。** 两者同名不同源，这是本次需求的核心。

补充事实：`allReceive` 的真实语义就是「该 user 的所有邮箱」，不是全站——
`mail-vue/src/i18n/zh.js:34-35`：「全收已开启：这个邮箱会显示所有邮箱的邮件」；
服务端同一时刻只允许一个 account 全收：`mail-worker/src/service/account-service.js:271-280`。

## 2. 网页版口径（证据）

1. **入口**：侧边栏账户区「所有账户」按钮 → `router.push('/all-email')`
   `mail-vue/src/layout/aside/index.vue:28`（整块受 `v-perm="'account:query'"` 控制，见 `:20`；按钮本身**没有** `all-email:query` 门槛）。
2. **页面**：`mail-vue/src/router/index.js:33-37` → `views/all-email/index.vue`；该页固定 `:type="'all-email'"`、`show-user-info`（`:12`）、`show-status`（`:13`），列表内显示 `toEmail`/`sendEmail`（`components/email-scroll/index.vue:139-145`）。
3. **请求**：`views/all-email/index.vue:300-302` → `allEmailList({emailId,size,page,category,...params})`，`params` 含 `type`（all/receive/send/delete/noone）、`userEmail`、`accountEmail`、`name`、`subject`、`keyword`、`timeSort`（`:132-141`、`:37-43`）。
4. **请求封装**：`src/request/all-email.js:3-5` 仅 `GET /allEmail/list`，**不传 accountId / userId**。
5. **按角色显示不同范围？** 不是"范围不同"，是"能不能进"：
   - 用户带 `all-email:query` 时，`src/init/init.js:45-48` 会在静态路由之后追加一条 `/all-mail` → `views/all-email/index.vue`（`src/perm/perm.js:111-120`），覆盖静态路由里同路径的「本用户全部邮件」页 `router/index.js:26-31`。
   - 也就是说：**同一路径 `/all-mail`，管理员看到全站页，普通用户看到自己全部的邮件页**。这是一个隐藏的角色分叉，建议后续单独清理。
   - 普通用户即使点到「所有账户」（`/all-email`）也会因为接口 403 而空列表——UI 与接口门槛不一致。
6. **网页版列表行不显示"所属用户"**：`userEmail` 服务端有返回（`email-service.js:1101-1104` 的 `leftJoin(user)`），但行内只用 `toEmail/sendEmail`（`components/email-scroll/index.vue:144`）。对"全站可见"而言，缺少「这封邮件属于谁」的标识。

## 3. 服务端口径（证据）

1. **普通邮箱接口 `/email/list`**：`mail-worker/src/service/email-service.js:31-226`
   - `allReceive=1` 只是把 `eq(email.accountId, accountId)` 换成 `eq(1,1)`（`:144`）
   - **`eq(email.userId, userId)` 恒定存在**（列表 `:145`、total `:179`、latest `:200`）
   - `eq(account.isDel, NORMAL)` 恒定存在（`:151`、`:184`）
   - `mailbox=all` → 仅 `is_del=0`（`:62`）；`typeCondition` 在 `mailbox=all/deleted` 时放开为 `1=1`（`:71`）
   - total 有 30 分钟 KV 缓存，键里带 `userId`（`:165-191`）
   → **现有参数无法绕开 `user_id`**，`allReceive` 不是全站。
2. **管理端接口 `/allEmail/list`**：`mail-worker/src/api/all-email-api.js:5-8` → `emailService.allList`
   `email-service.js:1011-1139`：
   - 条件里只有 `type` / `category` / `userEmail` / `accountEmail` / `name` / `subject` / `keyword` / `emailId` / `status != SAVING`（`:1035-1089`）
   - **没有 `email.userId`、没有 `account.isDel`**
   - 返回 `{...email, userEmail}`（`:1101-1104`），即带 `userId`、`accountId`、收件邮箱原文
   - `total` 无 KV 缓存（`:1106-1109`、`:1118`），每页都执行一次全表 `count()`——这是 D1 读取的主要放大点
3. **管理端删除 `/allEmail/delete`**：`api/all-email-api.js:10-13` → `physicsDelete`（`email-service.js:882-888`）**按 emailId 物理删除，无 userId 过滤**。换言之 `all-email:delete` 是一个可以删掉任何人邮件的权限位（风险项，见 §7）。
4. **管理端最新邮件 `/allEmail/latest`**：`email-service.js:1141-1159` 同样无 `user_id` 过滤（全站轮询新邮件）。
5. **详情/读/星/分类仍按 userId**：`detail`（`:1352-1375`，`eq(email.userId, userId)` 不满足直接报 `authExpired`）、`read/unread`（`:1246-1257`）、`moveCategory`（`:1259-1267`）。→ 全站列表点开别人的邮件在服务端会失败；`starId` 也只会匹配当前 userId（`:132-137`）。
6. **现有管理端其它页面**：`/user/allAccount`（`account-service.js:242-260`）是**指定 userId** 的账户分页，不是全站 account 列表；没有找到 `/admin` 之类"全站账户"路由。

## 4. 权限模型

1. 权限表初始化：`mail-worker/src/init/init.js:813-815`
   ```
   (27, '邮件列表', '', 0, 1, 4)          // 菜单组
   (28, '邮件查看', 'all-email:query', 27, 2, 0)
   (29, '邮件删除', 'all-email:delete', 27, 2, 0)
   ```
2. 路由守卫：`security.js:46-49`（`/allEmail/*` 在 requirePerms 列表）→ `:96-97` 映射到 `all-email:query` / `all-email:delete` → `:167-186` 校验：命中权限路径放行；否则 **`user.type === 0`（系统管理员）放行**，其余 403。
3. 权限来源：`perm-service.js:27-44`，`user.type` 当 `roleId` 用（`leftJoin(role, eq(role.roleId, user.type))`），支持 `user_perm` 覆写；`user-service.js:44,63-66` 中站点 admin 邮箱直接拿 `'*'` 且 `type=0`。
4. **没有**"查看全部邮件"之外的能力位；`role.availDomain` 只限制「这个角色能绑定/收信哪些域名」（`account-service.js:86`、`login-service.js:97`、`email/email.js:86-88`），与邮件可见范围无关；role 表也没有 `type` 字段（`src/entity/role.js` 只有 `sendType/accountCount/availDomain`）。
5. 结论：**"看全站邮件"是已有能力，但只挂在 `all-email:query` 这个后台权限键上**，不是新能力；把入口/范围给普通用户才属于产品决策。

## 5. 若要给客户端"全站所有邮箱"，建议方案

> 下列为方案建议，本轮**未落地**。

### 方案 A（推荐，改动最小）：复用 `/allEmail/list`

- 服务端：不新增接口，客户端直接调 `GET /allEmail/list`；
- 权限：沿用 `all-email:query`（`security.js:96`），客户端在设置页/入口处按 `permKeys.contains("all-email:query")` 控制是否显示；
- 缺口需补齐（都要服务端动，属于另一件事）：
  1. `allList` 缺少 `mailbox` 语义（当前只有 `type=receive/send/delete/noone` + `category`），也没有 `is_del=0`、`spam=0` 的默认过滤 → 默认会混入已删除邮件（`email-service.js:1037-1055` 无 isDel 条件）；
  2. 无 `account.isDel` 过滤 → 已删账户的邮件仍会出现；
  3. `total` 无缓存，全表 count 会放大 D1 读取（`:1106-1119`）；
  4. 没有"按账户/按用户"的筛选参数，无法做客户端账户筛选器；
  5. 详情/已读/星标/分类全部按 userId 拒绝（§3.5），全站列表只能是**只读**，或另开站点级详情接口。

### 方案 B：新增 `scope=site`

- 在 `email-service.js:list()` 里按 `scope=site` 去掉 `eq(email.userId, userId)`（`:145/:179/:200`），保留 `account.isDel=NORMAL`；
- **必须是新的独立路由/接口**（例如 `GET /siteEmail/list`），并在 `security.js` 的 `requirePerms` 里绑定新权限键（如 `email:site-query`）；
- 绝不能只在现有 `/email/list` 上放开 `scope` 参数——`/email/list` 无权限守卫，任何登录用户传 `scope=site` 就能读全站，是明确越权。
- SQL 放开清单：
  - `email.userId`：去掉（唯一必须放开的）
  - `account.isDel`：**保留**（避免已删账户串进来）
  - `email.isDel`：按 pills 语义保留（`mailbox=all` → `is_del=0`）
  - `star` join：`eq(star.userId, userId)` 保留（别人邮件的星标本来就不该显示）
- 返回字段：`userId`、`accountId`、`userEmail`（现有 `/email/list` 已返回前两个，`userEmail` 需再 join 一次 `user`）。

## 6. 客户端改动点（Android，待产品确认后再做）

1. **请求**：新增 `Api.siteEmailsRaw(...)` 走 `/allEmail/list` 或 `/siteEmail/list`；`allEmailsRaw`（`Api.kt:429-444`）保持不动，避免影响现有管理页。
2. **列表分组**：7 个账户以上必须分段——按 `accountId` 分组（或顶部加账户筛选器）；不建议把全站邮件混在一张平铺列表里。
3. **行内信息**：必须显示「收件邮箱 + 所属账户/用户」，否则无法判断归属；现有 `AdminScreens.kt:127` 只在多账户时做本地 accountId→email 映射，全站范围不够，需要 `userEmail` 字段。
4. **计数语义**：`/email/menu-counts` 的徽标固定按 `user_id` 统计（`email-service.js:1271-1291`，`FROM email_count WHERE user_id = ?`），**不能**直接当全站 total 用；全站 total 要用列表接口返回的 `total`，并在 UI 上明确区分（例如「全站 12,345 封」vs「我的 764 封」）。
5. **入口**：仅在 `permKeys` 含 `all-email:query`（或 `*`）时展示入口；现有 `AdminLinks.kt:23` 的「全部邮件」不应默认变成全站页，否则普通用户会 403。

## 7. 风险

| 风险 | 说明 |
|---|---|
| 越权可见 | `all-email:query` 一旦发给普通角色，该角色即可读全站邮件（含正文摘要、发件人、收件人）。网页版已有的这个口子就是现状，不是新引入，但客户端扩面会放大暴露。 |
| 越权删除 | `all-email:delete` → `physicsDelete` 无 userId 过滤（`email-service.js:882-888`），是物理删除、无法恢复。 |
| D1 每日读取配额 | `/allEmail/list` 每次请求都做全表 `count()`（无缓存，`:1106-1119`），大列表 + 无限滚动会成倍放大 `rowsRead`（免费档 5,000,000/天）。 |
| 总数缓存 | 全站 total 若沿用 `/email/list` 的 30 分钟 KV 缓存策略，需要独立 key（不能带 userId），否则不同用户互相串数。 |
| 详情不可用 | 点开别人的邮件会 `authExpired`（`:1352-1375`），全站列表暂时只能是只读列表。 |
| 现有 UI 门槛不一致 | 网页版「所有账户」按钮不带权限门槛，无权限用户点进去是 403 空页；客户端若照搬入口会出现同样问题。 |
