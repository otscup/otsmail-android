# OTS Mail Android：功能候选清单（别人有、我们还没有）

> 口径：只读盘点，未改动源码。判断依据来自当前客户端代码与 `mail-worker` 服务端路由；拿不准的标「未验证/推断」。
> 价值/成本是产品判断，不是工时承诺。成本口径：低 = 主要是客户端 UI + 复用现有接口；中 = 两端都要改但不动核心协议；高 = 需要改数据模型、协议或引入加密/第三方 SDK。

## 先说结论

- **最划算的三项**：定时发送（本地加密队列、AlarmManager 调度、服务端 `/email/schedule` 都已就绪，只缺写信页入口和定时列表 UI）、多账号快速切换（账户抽屉已有，只缺“最近账户”一键位）、邮件模板（纯客户端，零服务端改动）。
- **最该补的“专业感”**：每账户独立签名、通知内快速回复、附件管理（缓存上限/批量保存）、无障碍审计。
- **投入大但收益不确定**：会话聚合、用户自定义规则、标签/文件夹。它们都要动数据模型，且和“统一收件箱 + AI 分类”的现有形态有重叠。
- **不建议优先做**：已读回执、S/MIME/PGP、营销式群发。前两个生态支持差、隐私代价高；第三个有反滥用风险。
- **现有优势不要丢**：AI 摘要/回复/润色/翻译、外部 IMAP 常驻收信 + 归档、统一收件箱、图片代理、8 秒撤销发送、批量操作、管理员全站搜索。这些已经是差异化能力。

## 一、点名覆盖的 16 项

| 功能 | 现状 | 用户价值 | 实现成本 | 依赖服务端 | 隐私/权限代价 | 依据与说明 |
|---|---|---|---|---|---|---|
| 定时发送 | **基础设施已实现，UI 入口未接** | 高 | 低 | 是（已有接口） | 低 | 客户端已有加密本地队列、去重、换时区重算（`data/ScheduledSend.kt`）、AlarmManager 调度与开机/改时间恢复、失败通知（`schedule/ScheduledSendScheduler.kt`，Manifest 已注册 receiver）；但 `ui/ComposeScreen.kt` 里搜不到“定时”入口，也没有定时邮件列表页。服务端 `POST /email/schedule` 已支持（最多提前 30 天，`mail-worker/src/api/email-api.js:85`、`email-service.js:1501`）。补：写信页“发送时间”选择 + 定时列表（取消/改时间/失败重试） |
| 邮件签名 | **部分已有** | 高 | 低 | 是（当前签名存服务端） | 低 | 设置页有“签名”分组，写信页可插入；缺“每账户独立签名”“按新邮件/回复切换签名” |
| 自动回复 / 休假回复 | **缺失** | 中 | 中高 | 是（收信链路） | 低 | 服务端无相关路由；需要按账户开关、按发件人去重（同一个人一天只回一次）、避免自动回复互踢（`Auto-Submitted` 头判断）。做不好会形成邮件环路 |
| 规则分类与过滤 | **部分已有（不可编辑）** | 高 | 中 | 是 | 中 | 服务端已有内置规则 `builtin-rules.js` 和 AI 六分类，但用户不能自定义；“规则”只在管理员设置里选类型。补：客户端规则编辑器（发件人/主题/关键词 → 分类/星标/归档/提醒），服务端执行并回传命中原因 |
| 会话聚合 | **缺失** | 高 | 高 | 是 | 低 | 现在列表是扁平邮件，没有 `threadId`；需要服务端生成会话、客户端换列表/详情形态。会改变现有“一封一行”的交互与分页，属结构性改造 |
| 标签与文件夹 | **部分已有（固定形态）** | 中 | 高 | 是 | 低 | 现有 inbox/sent/trash/spam/starred + 6 个 AI 分类，没有用户自建标签或文件夹；外部邮箱目前只保证收件箱（**未验证**：其他文件夹是否同步）。自建文件夹还要处理 IMAP 文件夹同步与移动语义 |
| 全文搜索 | **已有，质量可提升** | 高 | 低（改进中） | 是（自有邮箱）；外部邮箱走本地 | 中 | 服务端 `keyword` 是 `%关键词%` 子串匹配（主题/正文/收发件人），没有全文索引；外部邮箱只搜本地摘要/正文。缺：搜索高亮、附件内容、结果排序、最近搜索 |
| 附件管理与预览 | **部分已有** | 中 | 中 | 部分（大附件/云附件需要） | 低 | 详情页可预览/下载，单文件 10 MB 上限（`data/Attachments.kt`）；缺总容量上限、按邮件/按账户清理、批量保存、附件列表页。缓存写在 `cacheDir`，无 LRU |
| 群发与密送 | **已有（普通多收件人）** | 中 | 已完成 | 否 | 低 | 写信页有抄送/密送；缺“通讯组/群发名单”和发送频率保护。营销式群发不建议做，反滥用与投递声誉成本高 |
| 模板 | **缺失** | 中 | 低 | 否（本地即可） | 低 | 纯客户端：模板 CRUD + 写信页插入 + 变量（收件人/日期）。若要多设备同步才需要服务端 |
| 已读回执 | **缺失** | 低 | 高 | 是 | 高 | 需要生成/解析 MDN、征得收件人同意；多数客户端默认忽略，且会暴露阅读行为。除非企业合规要求，不建议优先 |
| S/MIME 与 PGP | **缺失** | 低（企业合规场景为中） | 高 | 部分 | 高 | 需要证书/密钥管理、签名验签、加解密、KeyStore/OpenKeychain 集成；外部 IMAP 账户的密钥还要本地保管。误操作会导致“签名无效/无法解密”的支持成本 |
| 多账号快速切换 | **部分已有** | 高 | 低 | 否 | 低 | 已有账户抽屉；缺“最近使用账户”一键切换、写信页发件身份快速切换、统一收件箱与单账户视图的显式切换 |
| 桌面小组件 | **缺失** | 中 | 中 | 否（读本地快照） | 中 | 需要 Glance/AppWidget + 独立于前台服务的数据读取；锁屏/桌面可见会泄露主题与发件人，需要“隐藏内容”开关 |
| 快捷操作与手势 | **部分已有** | 中 | 低中 | 否 | 低 | 已有左右滑操作、长按多选、撤销删除、点击区域封装；缺自定义映射、通知内快速回复/归档、长按快捷菜单 |
| 无障碍 | **部分已有** | 高 | 中 | 否 | 无 | 全项目约 44 处 `contentDescription`，但没有系统性 TalkBack/字体缩放/对比度审计；自绘图标与滑动操作是高风险点。属于合规与口碑项 |

## 二、值得补充的候选（不在点名清单内）

| 功能 | 用户价值 | 实现成本 | 依赖服务端 | 隐私/权限代价 | 说明 |
|---|---|---|---|---|---|
| 撤销发送 | 高（**已有**） | — | 否 | 低 | 已有 8 秒撤销窗口（`ui/ComposeScreen.kt:176`）；可考虑把时长做成设置项 |
| 稍后提醒（Snooze） | 中 | 低中 | 是（或本地 WorkManager） | 低 | 把邮件暂时移出收件箱、到点回到未读；比“定时发送”更常用 |
| 通知内快速回复/归档 | 高 | 中 | 否 | 中 | 需要通知 Action + 本地待发队列；锁屏可见内容要注意隐私 |
| 离线发件队列 | 中高 | 中 | 是（已有 `/email/send` 重试） | 低 | 弱网下先落本地队列，联网自动发送；要防止重复发送（幂等键） |
| 一键退订（List-Unsubscribe） | 中 | 低 | 否 | 低 | 解析邮件头，展示“退订”按钮；营销邮件体验提升明显 |
| 大附件/云附件链接 | 中 | 中高 | 是 | 低 | 超过 10 MB 的附件改上传到服务端并生成链接；需要存储配额与过期策略 |
| 日历邀请解析 | 中 | 中 | 部分 | 低 | 识别 `text/calendar`，显示“接受/暂定/拒绝”并写系统日历；需要日历权限 |
| 邮件导出/打印 | 低中 | 低 | 否 | 低 | 导出 `.eml`/PDF；适合合规留档 |
| 防钓鱼提示 | 中高 | 低中 | 部分 | 低 | 展示真实发件域、可疑链接、外部图片提示；现有图片代理可作为基础 |
| 每账户独立签名/别名 | 中高 | 低 | 是（现有签名字段扩展） | 低 | 商务多账号场景刚需；可与“快速切换”一起做 |
| 联系人分组/最近联系人 | 中 | 低 | 否 | 中（通讯录权限） | **部分已有**：收件人自动补全只从邮件历史取候选，按频次/最近使用/拼音首字母排序，不申请通讯录权限（`ui/RecipientSuggest.kt`）；缺系统通讯录、分组、手动收藏 |
| 规则命中说明 | 中 | 低 | 是 | 低 | 给 AI 分类加“为什么归到这里”，提升信任，降低误分类投诉 |

## 三、排期建议

**第一批（1–2 周量级，低风险、可直接提升体验）**

1. 定时发送客户端入口（复用 `/email/schedule`，含取消/修改）。
2. 多账号快速切换（最近账户 + 写信身份切换）。
3. 邮件模板（本地 CRUD + 插入）。
4. 每账户独立签名 + 回复/转发签名策略。
5. 通知内快速回复/归档（先做“标记已读/归档”，不做完整回复）。
6. 无障碍专项审计（TalkBack 走查、触控区、字体缩放、对比度）。

**第二批（需要服务端配合，改动可控）**

1. 规则编辑器 + 命中说明（复用现有分类与 `builtin-rules`）。
2. 附件管理（总容量上限、LRU、批量保存、按账户清理）。
3. 稍后提醒（Snooze）。
4. 一键退订 + 防钓鱼提示。
5. 桌面小组件（先做“未读数 + 最近 5 封”，带隐藏内容开关）。

**第三批（结构性改造，先做方案再排期）**

1. 会话聚合（需要 `threadId`，会改列表/详情/分页）。
2. 用户自建标签/文件夹（需要同步语义与外部 IMAP 文件夹支持）。
3. S/MIME 或 PGP（若确有企业合规客户，先做 S/MIME 验签与解密，PGP 后置）。
4. 已读回执（仅在企业场景评估，默认关闭）。
5. 自动回复/休假回复（必须带环路保护与去重，否则不建议上线）。

## 四、明确不建议/暂缓

| 项 | 原因 |
|---|---|
| 营销式群发 | 投递声誉、反滥用、退订合规成本高；现有 cc/bcc 已覆盖正常群发 |
| 已读回执默认开启 | 生态支持差、隐私争议大；做成“可选且默认关闭”才有意义 |
| PGP 全量支持 | 密钥管理复杂、支持成本高；没有明确客户需求前投入产出比低 |
| 用 AI 做“全自动归档/删除” | 误判代价高；规则应先“建议”再“执行”，并保留撤销 |
| 第三方邮件也走服务端 FCM | 服务端目前没有第三方触发点（`ExtIdleService.kt:70` 注释）；在补齐前不要把 IDLE 关掉，否则等于关闭提醒 |

## 五、判断依据与未验证项

- 定时发送、签名、分类、搜索的服务端能力来自 `mail-worker` 的 `email-api.js` / `email-service.js` / `builtin-rules.js` / `ai-service.js`。
- 客户端已有能力来自 `ui/ComposeScreen.kt`（抄送密送、撤销发送、草稿、附件）、`ui/DetailScreen.kt`（附件预览、标记已读）、`ui/SettingsScreen.kt`（签名、外部邮箱）、`ui/InboxScreen.kt`（分类、批量、滑动）、`data/Attachments.kt`（10 MB 上限）。
- **未验证**：外部 IMAP 账户除收件箱外是否同步其他文件夹；规则在服务端的具体执行时机（收信时/查询时）；搜索在真实数据量下的延迟；TalkBack 实际可用性；通知 Action 在国产 ROM 上的兼容性。
- 成本评级不含测试与灰度成本；涉及协议/加密的功能（S/MIME、PGP、已读回执）实际投入通常比表内评级高一档。
