# 去重与统一收件箱 · 方案

> 只读调研，未修改任何代码。本文只回答「同一封邮件为什么出现两份、按什么判重、在哪一层去重、合并后怎么交互」，并给出改动量预估与后续规划。

## 0. 结论先行

- 现象根因：同一封 Gmail 邮件走了两条独立链路——一条是 Gmail 自动转发到 otsmail（进服务端 `email` 表），一条是把 Gmail 作为第三方邮箱绑定后由 IMAP 同步到本地 `ext_mail` 表。两条链路各自去重，但彼此不知道对方存在。
- 推荐判重键：**归一化后的 RFC 5322 `Message-ID`，仅在「服务端邮件 ↔ 第三方邮件」之间做跨源匹配，且限定同一用户**。Gmail 自动转发通常原样保留原始 `Message-ID`，而正常连发的两封邮件各自有不同的 `Message-ID`，因此它既能合掉转发副本，又不会误合同人连发的两封。
- 兜底：只有两侧都拿不到真实 `Message-ID` 时，才用「发件人地址 + 归一化主题 + 时间差 ≤ 5 分钟」。
- 服务端列表接口**已经返回 `messageId`**（`/email/list` 的查询里已 select），客户端 `MailItem` 目前丢弃了它；补一个字段即可，**v1 不需要服务端改动，也不需要数据库迁移**。
- 去重放在「合并后的展示层」而不是入库层：两份都保留，列表只渲染主份，另一份收进「重复」入口。这样可逆、不丢源数据，点开、已读、删除也能逐份处理。
- 只在列表层去重不够：已读要同步两份，否则被隐藏的那份会在「未读」里反复冒出来；通知需要跨源按 `Message-ID` 去重（要服务端 FCM 载荷补一个字段）；未来全文索引只能索引主份。

## 1. 现状：聚合收件箱是怎么合表的

### 1.1 两套数据、两套主键

| 维度 | 服务端邮件（转发副本） | 第三方邮箱（原始副本） |
|---|---|---|
| 存储 | 服务端 `email` 表，客户端经 `/email/list` 拉取 | 本地 SQLite `ext_mail` 表 |
| 主键 | `email_id`（自增） | `local_id`（本地自增） |
| 业务唯一键 | 无跨源唯一键；入站时有 `(message_id, to_email, type, status)` 去重 | `(ext_id, message_id)` 唯一索引 |
| 时间字段 | `create_time`，默认 `CURRENT_TIMESTAMP`，是**收信时间**，不是原始 `Date` | `date_ms`，优先取 `Date` 头，缺失时用 IMAP `INTERNALDATE` |
| 排序 | 按 `email_id DESC` | 按 `date_ms DESC, local_id DESC` |
| 内容来源 | Gmail 转发后的副本（From/Subject/正文通常保留） | Gmail 原邮箱经 IMAP 拉到的原始邮件 |

关键代码位置：

- 服务端列表查询：`mail-worker/src/service/email-service.js:122-154`，其中 `:143` 已经 `select email_id, ..., message_id, create_time`；排序在 `:180-184`。
- 服务端入站去重：`mail-worker/src/email/email.js:106-130`，按 `message_id + to_email + type=0 + status` 查重，命中则直接丢弃本次投递。
- 第三方归档去重：`mail-worker/src/service/ext-mail-service.js:184-188`，按 `(ext_id, message_id)` 去重。
- 本地第三方表：`app/src/main/java/com/otscup/otsmail/data/ExtMailStore.kt:146-171` 做 `INSERT OR REPLACE`，`:459` 建 `(ext_id, message_id)` 唯一索引；列表查询在 `:215-241`。
- 第三方同步入库：`app/src/main/java/com/otscup/otsmail/data/ExtSync.kt:332-334` 取 `Message-ID`，缺失时退化为 `uid:<uidValidity>:<uid>`；`:373-392` 批量 upsert。
- `Message-ID` 解析：`app/src/main/java/com/otscup/otsmail/data/MimeParser.kt:78`，取 `message-id` 头并 trim。

### 1.2 合并与排序

聚合列表由 `InboxMerge.merge` 完成，见 `app/src/main/java/com/otscup/otsmail/data/InboxMerge.kt:33-72`：

- 服务端行主键：`s:<emailId>`（`:38-41`），时间取服务端 `time` 解析出的 epoch。
- 第三方行主键：`x:<extId>:<localId>`（`:60-71`），时间取 `dateMs`。
- 最后统一按时间倒序：`:71` 的 `sortedByDescending`。

### 1.3 现有去重逻辑盘点

| 位置 | 去重范围 | 是否解决本次问题 |
|---|---|---|
| 服务端 `email.js:106-130` | 同一收件地址的重复投递 | 否，转发副本和 IMAP 副本不在同一张表 |
| 服务端 `ext-mail-service.js:184-188` | 同一第三方账号、同一 `Message-ID` | 否，只覆盖第三方内部 |
| 本地 `ExtMailStore` 唯一索引 | 同一 `ext_id` 下的 `message_id` | 否，只覆盖第三方内部 |
| `InboxMerge.merge` | **没有任何去重**，只做合并与排序 | 否，两份都会渲染 |

结论：当前是「三处各自去重，跨源零去重」。这就是同一封邮件出现两份的直接原因。

### 1.4 客户端目前拿不到服务端的 `Message-ID`

服务端 `/email/list` 已经把 `messageId` 放进返回体，但客户端 `MailItem` 没有这个字段，`Api.kt` 的列表解析也没有读它：

- `app/src/main/java/com/otscup/otsmail/data/Api.kt:53-76`（`MailItem` 字段）
- `app/src/main/java/com/otscup/otsmail/data/Api.kt:1084-1102`（列表 JSON → `MailItem`）

这是本次方案最便宜的一个改动点：补字段、补解析，跨源判重所需的数据就齐了。

## 2. 判重键选型

### 2.1 候选对比

| 候选键 | Gmail 自动转发 | 多账号收到同一封 | 同人连发两封同样内容 | 主要风险 |
|---|---|---|---|---|
| RFC 5322 `Message-ID` | 通常原样保留，可匹配 | 同 ID，会合；需限定「只跨源、同用户」避免过度合并 | 每封 ID 不同，不会误合 | 少数转发实现会重写或缺失；`uid:` 伪 ID 不能参与匹配 |
| 发件人 + 主题 + 时间 | 主题/发件人通常保留；时间要用「原始 Date vs 收信时间」的容差 | 有概率误合（同发件人、同主题、时间接近） | **会误合**，这是它最大的问题 | 同人短时间内连发同主题邮件会被当成重复 |
| 正文哈希 | 转发可能重排/包装/改编码，哈希不稳定 | 有概率误合 | 正文相同就会误合 | 空正文、模板正文、签名差异都会造成误判；服务端列表正文只有截断片段，算全量哈希还得逐封拉详情 |

### 2.2 三种场景的具体表现

**场景 A：Gmail 自动转发**

- `Message-ID`：Gmail 自动转发通常沿用原始 `Message-ID`（它自己也依赖这个头做环回检测）；到达 otsmail 后写入 `email.message_id`。IMAP 侧解析同一封原始邮件，得到同一个值。**可合，且不会误合。**
- 发件人+主题+时间：发件人、主题通常一致；但服务端列表的 `time` 是收信时间，IMAP 侧是原始 `Date`，两者相差一次转发延迟（正常 1～3 秒，队列拥塞时可能几分钟），必须设容差。**可合，但容差越大误合概率越高。**
- 正文哈希：转发链路可能重排 HTML、补 `Received`/`Resent-` 头、改编码或加签名，哈希可能不一致；反过来，两封不同邮件正文相同（例如都只有一句「收到」）又会撞哈希。**不稳定。**

**场景 B：多账号收到同一封**

例如同一封群发同时进了 Gmail 和另一个第三方邮箱，或同一封邮件被转发到两个 otsmail 地址：

- `Message-ID`：内容确实是同一封，ID 相同；如果无脑全局合并，会把「不同收件人、不同已读状态」的两份合成一份。**需要通过「只跨源、不跨同源」限制范围**：v1 不做「服务端 ↔ 服务端」和「第三方 ↔ 第三方」的合并。
- 发件人+主题+时间：同样会合，且误合范围更大。
- 正文哈希：同样会合。

**场景 C：同一个人连发两封内容相同的邮件**

- `Message-ID`：两封各自生成新 ID，**不会误合，这是它相对另外两种方案的决定性优势。**
- 发件人+主题+时间：如果两封间隔在容差内，**会被误合**。
- 正文哈希：**一定会被误合**（如果正文完全一致）。

### 2.3 推荐规则

**主键：归一化 `Message-ID`。**

归一化步骤（两侧用同一函数）：

1. 取原始头，trim；
2. 去掉首尾的 `<`、`>`；
3. 转小写（实际部署中 `Message-ID` 的大小写不敏感，统一小写可避免 Gmail/IMAP 两侧大小写差异）；
4. 空值、不含 `@`、或以 `uid:` 开头的值一律视为「无真实 Message-ID」，不参与主键匹配。

匹配范围：

- 只在「服务端行」与「第三方行」之间匹配；
- 只在同一用户内匹配（聚合列表本身就是当前用户的数据）；
- 一个第三方行最多挂到一个服务端主份上；多个候选时取时间最接近的一个，不做扇形合并；
- 服务端行之间、第三方行之间 v1 不互相去重。

**兜底：发件人 + 主题 + 时间。**

仅当两侧都没有真实 `Message-ID` 时启用：

- 发件人：只比较邮箱地址、转小写，忽略显示名；
- 主题：去掉连续的 `Re:` / `Fw:` / `Fwd:` / `回复:` / `转发:` 前缀，压缩空白，转小写后精确相等；
- 时间：`|服务端 create_time - 第三方 date_ms| ≤ 5 分钟`；
- 仍然只跨源、同用户、一对一匹配。

这条兜底会误合「同人 5 分钟内连发两封同主题邮件」，属于已知代价；因为只在缺 `Message-ID` 时生效，实际触发面很小。

**不推荐正文哈希。** 它既可能漏合（转发改写正文），又可能误合（模板正文/空正文），而且要做全量正文哈希必须逐封拉详情，成本远高于收益。正文相似度最多只能作为「查看重复」页里的辅助说明，不应参与判重。

### 2.4 需要先验证的两个事实

1. **真实样本里 Gmail 转发的 `Message-ID` 是否保留。** 建议上线前抽 5～10 封真实邮件，对比服务端 `email.message_id` 与本地 `ext_mail.message_id`。如果保留率高（预期如此），主键方案直接成立；如果发现被重写，再决定是否启用兜底或调整转发方式。
2. **是否存在重复 `Message-ID` 头。** 当前 `MimeParser` 用 map 收集头，后出现的同名头会覆盖先出现的（`MimeParser.kt:78` 附近）。如果转发链路追加了第二个 `Message-ID`，可能取到错误值。真实样本里若出现双头，应改为「保留第一个」或收集多个候选；这属于 1～2 行的小修，不改变整体方案。

## 3. 去重应该作用在哪几层

### 3.1 列表展示（必须）

在 `InboxMerge.merge` 排序之后加一个去重分组步骤，输出：

- `visible`：实际渲染的行；
- `duplicatesOf[primaryKey]`：被隐藏的副本列表（含来源、时间、已读/星标状态）。

主份固定选服务端行，原因见 4.1。分组只在当前列表范围内计算，不持久化；切换文件夹、搜索、分页时重新计算。

### 3.2 未读数

现状：抽屉/角标计数来自 `Api.menuCounts`，**只统计服务端邮件**；第三方邮件的未读没有计入角标（`InboxScreen.kt:390-400` 附近）。因此隐藏一份第三方副本不会让角标变少，也不会变多。

但有两个后遗症要处理：

- 「未读」入口当前把第三方邮件也带进来，而 `ExtMailStore.feed` 没有按 `seen` 过滤（`ExtMailStore.kt:215-241`）。也就是说已读的第三方邮件也会出现在未读列表里，这是既有缺口。去重后，分组的未读点应取「任一副本未读」，否则用户会在未读列表里看到一行却没有未读点。
- 点开主份时如果只把服务端那份标已读，隐藏的第三方副本仍是未读；下次刷新，分组未读点又会亮起，形成「读了还在」的假象。所以**已读必须同步两份**（见 4.3）。

如果后续把第三方未读并入角标，计数必须以「去重后的组」为单位，而不是以行为单位。

### 3.3 搜索结果

服务端搜索和第三方搜索目前走同一条合并管线（`InboxMerge`），因此把去重放进 `InboxMerge` 后，搜索结果天然生效。

要注意两点：

- 服务端搜索只能搜到转发副本，第三方搜索只能搜到原始副本。两边的命中原因可能不同（例如转发副本正文被改写），去重只是展示层合并，不改变「谁命中」。
- 如果未来新增独立的搜索入口或服务端统一搜索，必须复用同一个去重函数，不能在 UI 层各写一套。

### 3.4 通知

现状是两条独立通道：

- 服务端 FCM：`emailId` 作为去重键，载荷里**没有 `messageId`**（`mail-worker/src/service/fcm-service.js:76-87`，调用点 `email.js:244-252`）。
- 第三方 IDLE：本地按 `extId|messageId` 去重（`PushDedupe.kt:62-70`）。

所以同一封邮件可能先收到转发副本的 FCM 通知，再收到第三方 IDLE 通知，用户看到两次提醒。

要彻底解决，需要：

1. 服务端在 FCM data 里补 `messageId`（`email.js` 调用处传入 `emailRow.messageId`，`fcm-service.js` 放进 data），约 3～5 行；
2. 客户端通知去重键改为「跨源 `messageId` 优先，拿不到再退回 `emailId` / `extId|messageId`」；
3. 保留一个短时间窗（例如 10 分钟），避免同一 `Message-ID` 在不同来源之间反复触发。

如果 v1 不想动服务端，也可以先只做列表去重，通知重复作为已知遗留项；但不能声称「已完全去重」。

### 3.5 本地全文索引（未来）

未来正文入索引时，必须**按组只索引主份**，或者在索引里记录 `groupKey`，搜索后按组折叠。否则列表已经去重，搜索仍会返回两条。

索引还需要注意：服务端正文当前是列表截断片段，第三方正文是本地完整正文；两侧可索引的字段并不对等。这部分留到后续规划，不在 v1 范围。

### 3.6 只在列表层去重的后遗症

| 后遗症 | 具体表现 | 处理 |
|---|---|---|
| 点开的是哪一份 | 列表只显示主份，通知深链或旧缓存可能指向被隐藏的第三方副本 | 通知/深链统一解析到主份；「查看重复」里可以显式打开副本 |
| 已读不同步 | 主份已读、副本未读，未读入口反复出现该组 | 打开主份时同时标记两份已读 |
| 删除不同步 | 删掉主份后副本还在，下一轮刷新又出现一行 | 默认删主份并把副本提升为可见；「查看重复」里提供逐份删除和「同时删除两份」 |
| 星标不同步 | 主份星标、副本未星标，星标文件夹里可能少一条 | v1 星标只作用于主份；需要双向同步时在副本操作里显式处理 |
| 分页/筛选边界 | 主份在服务端第 2 页、副本在第三方窗口内，跨页无法匹配 | 只在当前已加载窗口内去重；跨页重复允许短暂存在，滚动加载后自然合并 |
| 计数口径 | 角标只算服务端，第三方未读未计入 | 现状即如此；未来统一未读时按组计数 |

## 4. 合并后的交互

### 4.1 显示哪一份

**默认显示服务端（转发）副本。** 理由：

- 服务端行的读/星标/删除/分类/搜索/未读计数都在现有主流程里，交互完整；
- 转发副本是 otsmail 的「正式收件」，删除只影响 otsmail，不会误删 Gmail 原邮箱；
- 第三方副本作为源邮箱镜像保留，需要时从「查看重复」进入。

代价：服务端行的 `create_time` 是收信时间，列表时间会显示转发到达时间，而不是原始发送时间。正常转发延迟只有几秒，用户基本感知不到；如果延迟明显，可在「查看重复」里展示原始 `Date`。

不建议反过来以第三方副本为主份：它的操作面更窄（没有分类、部分入口不支持），且依赖 IMAP 在线状态；服务端副本更适合作为聚合列表的锚点。

### 4.2 另一份怎么隐藏、要不要「查看重复」入口

- 另一份不删除、不入库丢弃，只在当前列表分组里隐藏。
- 主份行尾加一个轻量标识（例如「重复 2」小徽标），不抢主信息。
- **需要「查看重复」入口**，否则被隐藏的副本在 UI 上完全不可达。建议放在行尾更多菜单和详情页更多菜单里，打开一个底部弹层：
  - 每份显示：来源标签（otsmail 地址 / Gmail 地址）、时间、已读/星标状态；
  - 每份提供：打开这一份、标记已读/未读、加星/取消、删除这一份；
  - 底部可选「同时删除两份」，需要二次确认并明确写出影响范围（服务端进 otsmail 垃圾箱；第三方进 Gmail 垃圾箱）。

如果第一版想更省，也可以只做「重复」徽标 + 点击后跳转到第三方详情；但体验上不如弹层清晰，后续仍要补。

### 4.3 已读、星标、删除分别怎么处理

| 操作 | 建议 |
|---|---|
| 打开主份 | 服务端 `markRead` + 对第三方副本 `ExtImapActions.setSeen(..., true)`；两边都成功后刷新列表 |
| 标记未读 | 同样两份一起改，避免只改一边导致分组状态抖动 |
| 星标 | v1 只改主份；「查看重复」里可单独给副本加星 |
| 删除主份 | 默认只删主份；删除成功后如果还有副本，立即把副本提升为可见，避免「删了又出现」 |
| 同时删除两份 | 只在「查看重复」弹层里提供，二次确认，文案写明两边各自的删除位置 |

已读同步是这次体验的关键：用户看到一行，读完后这一行必须真正消失/变已读，不能因为隐藏副本未读而复活。

### 4.4 分页与筛选

- 去重只在「当前已加载的服务端页 + 当前第三方窗口」内计算；
- 服务端还有下一页、或第三方窗口滑动后，重新计算分组；
- 跨页的同一封邮件允许短暂出现两份，加载完成后合并；不要为了跨页去重去拉全量数据；
- 分类、星标、垃圾箱等文件夹各自独立计算，不做跨文件夹合并（例如转发副本进了垃圾箱、原始副本在收件箱，不应互相隐藏）。

## 5. 能不能在入库阶段就去重

### 5.1 客户端入库阶段（ExtSync）

不建议在 `ExtSync` 写库时直接丢弃副本，原因：

- 入库时无法可靠知道服务端是否已经有同一封邮件：服务端可能还没收到转发，或用户还没拉取到那一页；
- 丢弃第三方行会失去原始 `Date`、原始正文、IMAP 操作入口和离线能力，且不可逆；
- 转发链路可能失败或被判垃圾邮件，第三方副本反而是唯一可用的一份；
- 服务端没有按 `messageId` 查询单封邮件的公开接口，逐封查询会引入明显的同步开销。

如果未来要做，至少需要服务端提供批量「按 `messageId` 查是否存在」的接口，并且只做「标记关联」，不要做「删除副本」。

### 5.2 服务端现有的去重能力

服务端已经有两套互不相通的去重：

- 入站投递：`mail-worker/src/email/email.js:106-130`，`(message_id, to_email, type, status)`；
- 第三方归档：`mail-worker/src/service/ext-mail-service.js:184-188`，`(ext_id, message_id)`。

它们都只解决「同一来源内的重复」，不解决「转发副本 ↔ IMAP 副本」。因此不能指望调大现有去重范围来解决本次问题。

### 5.3 服务端要不要做跨源关联

可选的后续增强，不是 v1 必需：

- 在第三方归档时，按 `user_id + message_id` 查一次 `email` 表，命中就在 `ext_mail` 记一个 `linked_email_id`；反过来在入站时查 `ext_mail` 也可以；
- 好处：关联关系持久化，换机/重装后仍能直接分组；为未来的统一未读、统一搜索提供权威链接；
- 代价：需要给 `ext_mail` 加列（数据库迁移）、处理「谁先到」的时序、以及转发链路失败时的悬空关联；
- 另一个现实约束：`ext_account.account_id` 在 v2 里固定为 0（`ext-account-service.js:195-201`），服务端无法仅凭账号表知道「这个 Gmail 转发到了哪个 otsmail 地址」，只能按 `user_id + message_id` 做用户级匹配。

**建议：v1 只做客户端展示层去重；等服务端要做统一未读/统一搜索时，再加 `linked_email_id` 这类持久关联。** 这样第一步零迁移、可回滚，也不会把两条链路的写入耦合在一起。

### 6.3 测试

## 7. 后续规划（暂不实施）

### 7.1 真正的统一收件箱

范围：多个 otsmail 账号与多个第三方邮箱混排成一个列表，统一未读角标、统一「未读」入口、统一搜索，并保留按账号筛选。依赖：本方案的去重分组必须先稳定；抽屉计数要从「只算服务端」扩展为「服务端 + 第三方、按组计数」；多账号分页需要服务端提供稳定的跨账号游标。大致顺序：先去重与已读同步 → 再统一未读计数 → 再做跨账号统一搜索。不要在去重还没稳定时先动计数，否则会重复加减。

### 7.2 高级搜索

范围：发件人、收件人、时间范围、是否带附件、文件夹/账号组合条件，支持与普通关键词叠加。依赖：当前服务端搜索是单字段 `searchType` 模式，第三方搜索是本地 SQL 的固定字段匹配，两边能力不对等；要做组合条件，需要服务端提供多条件查询参数，或先把第三方与本地缓存做成统一查询层。大致顺序：先统一搜索入口与结果去重 → 再做服务端多条件 API → 最后补第三方本地组合查询。

### 7.3 本地全文索引

范围：把正文写入本地索引，支持离线搜索、正文命中高亮、按账号/文件夹过滤。依赖：第三方正文已在本地 `ext_mail`，服务端正文目前只有列表截断片段，需要补详情缓存或服务端提供可索引正文；还要处理索引体积、加密存储、增量更新与删除同步。大致顺序：先做第三方正文的本地索引与离线搜索 → 再接入服务端已缓存正文 → 最后与去重分组、统一搜索合并。索引必须按组只保留主份，避免去重后搜索仍出现两份。
