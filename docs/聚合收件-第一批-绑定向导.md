# 聚合收件 · 第一批：绑定与连通性验证

范围：把 Gmail / Outlook / 163 / 126 / QQ 等第三方邮箱**绑进来并测通**。
本批不含：邮件拉取、统一收件箱展示、FCM / IMAP IDLE 推送（整体方案见 [聚合收件方案.md](./聚合收件方案.md)）。

## 1. 凭据表结构

新表 `ext_account`，与现有 `account`、`email`、`user` 表之间只通过 `user_id` / `account_id` 关联，凭据字段不落到任何已有表。

```sql
CREATE TABLE IF NOT EXISTS ext_account (
  ext_id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id        INTEGER NOT NULL,          -- 归属用户
  account_id     INTEGER NOT NULL,          -- 对应 account 表行，供收件箱按账户筛选
  provider       TEXT    NOT NULL,          -- gmail / outlook / netease163 / netease126 / qq / custom
  address        TEXT    NOT NULL,          -- 规范化小写邮箱
  auth_type      TEXT    NOT NULL,          -- app_password / auth_code / oauth
  secret_seal    TEXT    NOT NULL,          -- 密文 v1.<iv>.<ct>，明文永不入库
  secret_version INTEGER NOT NULL DEFAULT 1,-- 预留轮换密钥
  imap_host      TEXT    NOT NULL,
  imap_port      INTEGER NOT NULL,
  smtp_host      TEXT    NOT NULL,
  smtp_port      INTEGER NOT NULL,
  imap_idle      INTEGER NOT NULL DEFAULT 0,-- 服务器 CAPABILITY 是否含 IDLE，下一批推送用
  status         INTEGER NOT NULL DEFAULT 0,-- 0 正常 / 1 待复核 / 2 失效
  last_check_at  DATETIME,
  last_error     TEXT,                      -- 只存分类文案，不存服务器原始回显里的凭据
  create_time    DATETIME DEFAULT CURRENT_TIMESTAMP,
  update_time    DATETIME DEFAULT CURRENT_TIMESTAMP,
  is_del         INTEGER NOT NULL DEFAULT 0
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_ext_account_user_address
  ON ext_account(user_id, address) WHERE is_del = 0;
```

建表方式：`ensureSchema()` 在首次请求时 `CREATE TABLE IF NOT EXISTS`。原因：现有 `init()` 受 `init_done` 保护，新增迁移脚本不会在已部署实例上执行。

## 2. 加密方式

| 项 | 取值 |
| --- | --- |
| 算法 | AES-256-GCM（WebCrypto `crypto.subtle`） |
| 密钥 | Worker secret `EXT_CRED_KEY`，32 字节 base64，只存在服务端环境变量里 |
| IV | 每条记录独立随机 12 字节，与密文一起存 |
| AAD | `userId:accountId:provider`，把密文绑死在某个账号上 |
| 密文格式 | `v1.<iv-base64>.<ciphertext-base64>`，前缀留给未来的密钥/算法版本 |
| 明文生命周期 | 只在 `/ext/bind` 请求内存里出现一次，加密后立刻丢弃 |

隔离与泄露影响面：

- 独立密钥，不复用 JWT 签名密钥；`EXT_CRED_KEY` 泄漏不等于登录态泄漏，反之亦然。
- AAD 绑定账号 ⇒ 拿到库里密文也不能把 A 用户的授权码搬到 B 用户行下解密。
- 未配置 `EXT_CRED_KEY` 时 `/ext/bind` 直接返回 503，**不会退化成明文存储**。
- 凭据不进日志：`/ext/accounts` 只回元信息（不含 `secret_seal`）；错误信息只写分类（认证失败 / IMAP 未开），不回显授权码。
- 单条泄漏的影响面是「一个第三方邮箱的收信/发信权」；Gmail 应用专用密码、163/QQ 授权码都可以在网页端单独吊销，不牵连主密码。
- 客户端不落盘：授权码只在 `ExtBinder.state` 内存里，绑定完成或页面销毁即释放；不写 SharedPreferences，不写日志。

部署前置：

```powershell
# 生成 32 字节 base64 密钥（只需一次）
[Convert]::ToBase64String((1..32 | ForEach-Object { Get-Random -Maximum 256 }))
# 写入 Worker secret
npx wrangler secret put EXT_CRED_KEY
```

## 3. 绑定流程状态机

```
ADDRESS ──识别到服务商 / 转手动──▶ CREDENTIAL
CREDENTIAL ──「验证并绑定」──▶ 探测 IMAP + SMTP
      ▲                             │
      │                     失败（分类文案）
      └─────────────────────────────┘
                                    │ 两边都通过
                                    ▼
                                 SAVING ──服务端保存失败──▶ CREDENTIAL（提示「已验证，稍后重试」）
                                    │
                                    ▼
                                  DONE
```

- `ADDRESS`：只输邮箱，`ExtProviders.detect()` 自动补全 IMAP/SMTP 主机端口；未收录域名转「其他邮箱」手填。
- `CREDENTIAL`：选择授权方式 + 分步指引（去哪开 IMAP、在哪生成授权码）+ 填授权码；可返回上一步。
- 探测失败会停在 `CREDENTIAL`，保留已填授权码，按失败类型给不同提示。
- `SAVING` 失败同样退回 `CREDENTIAL`，并明确告知「连通性已通过，不用重新生成授权码」。
- `DONE` 后列表刷新，可「再绑一个」或解绑。

### 错误分类（决定界面文案）

| 分类 | 触发 | 文案方向 |
| --- | --- | --- |
| `HOST_UNREACHABLE` | DNS 失败 / 连接被拒 | 主机连不上，检查地址与网络 |
| `TIMEOUT` | 连接或读超时 | 换网络重试 |
| `TLS_FAILED` | SSL 握手失败 / STARTTLS 被拒 | 加密方式与规则表不符，改手动填端口 |
| `AUTH_FAILED` | IMAP `NO` / SMTP `535` | 授权码错误或未开第三方登录 |
| `IMAP_DISABLED` | IMAP 回 `BYE` / 含 disabled | 先去网页版开启 IMAP/SMTP |
| `SMTP_DISABLED` | SMTP 非 220、无 AUTH、530 | 已能收信但没开 SMTP |

## 4. 自动探测规则来源

真源：`mail-worker/src/utils/mail-providers.js`；客户端 `ExtProviders.kt` 是离线副本，两边必须同步。

| 服务商 | 域名 | IMAP | SMTP | 授权方式 | 置信度 |
| --- | --- | --- | --- | --- | --- |
| Gmail | gmail.com / googlemail.com | imap.gmail.com:993 SSL | smtp.gmail.com:465 SSL | 应用专用密码 | 官方帮助页 |
| Outlook | outlook.com / hotmail.com / live.com / msn.com / outlook.jp | outlook.office365.com:993 SSL | smtp.office365.com:587 STARTTLS | OAuth（本批占位） | 官方文档；基础认证已于 2024-09-16 停用 |
| 163 | 163.com / vip.163.com / 188.com | imap.163.com:993 SSL | smtp.163.com:465 SSL | 客户端授权码 | 官方帮助页；IMAP 需先发 `ID` |
| 126 | 126.com / yeah.net | imap.126.com:993 SSL | smtp.126.com:465 SSL | 客户端授权码 | 官方帮助页；`ID` 同上 |
| QQ | qq.com / foxmail.com | imap.qq.com:993 SSL | smtp.qq.com:465 SSL | 16 位授权码 | QQ 官方；foxmail.com 复用为推断 |

- 匹配规则：完全相等或 `*.域名` 后缀匹配，不做模糊猜测；未命中一律让用户手填。
- 手填模式只接受 993/143（IMAP）与 465/587（SMTP），主机名做正则校验，避免把服务端当成任意端口探测器。
- 非 `custom` 服务商忽略客户端传来的主机端口，一律用规则表，防止被改写成内网地址。
- 163/126 的 `ID` 命令、QQ 的短信验证步骤都写进了规则表的分步指引。

## 5. 本批真实可跑 / 占位

真实可跑：

- 服务端 `/ext/providers`、`/ext/accounts`、`/ext/bind`、`/ext/accounts/delete` 全部路由到真实 D1 读写。
- AES-GCM 加解密（`sealSecret` / `openSecret`）、`ensureSchema` 建表与唯一索引。
- 客户端 SSLSocket 直连的 IMAP `LOGIN`、SMTP `AUTH LOGIN` 探测，含 163/126 的 `ID` 前置与 STARTTLS 分支。
- 绑定向导三步 UI、错误分类文案、已绑定列表与解绑确认。
- `account` 表插入行（为下一批「顶部按账户筛选」预留）。

占位：

- Gmail / Outlook 的 OAuth：规则表里 `enabled=false`，界面显示「下一批」，不发起授权。
- `probe.imapOk/smtpOk` 本批由客户端实测后回传，服务端只做布尔校验；服务端复核放到第二批。
- 邮件拉取、统一收件箱合并、`Message-ID` 去重、FCM + IMAP IDLE 双通道推送：完全未做。
- `status` / `last_check_at` / `last_error` 字段已建但只在绑定时写入一次，尚无定期复核任务。
