# 聚合收件 · 第二批：拉取层与归档

范围：对已绑定的第三方邮箱做**只读增量拉取 → MIME 解析 → 本地落地 → 上传服务端归档**。
本批不含界面：没有统一收件箱、没有按账户筛选、没有推送、没有通知去重（见文末「真实可跑 / 占位」）。

## 0. 架构约束（本批按此实现）

| 约束 | 落地方式 |
| --- | --- |
| Workers 撑不住 IMAP 长连接与批量拉取 | IMAP 拉取全部在**客户端设备上直连**执行，复用第一批 `ExtProbe` 的 SSLSocket 能力 |
| 拉下来的邮件要能换机恢复 | 每封解析完立刻 `POST /ext/mail/archive` 上传，服务端只做**存储与查询**，不承担拉取 |
| 将来可能挪到常驻容器 | **不做预留抽象**：没有 `PullProvider` 之类的空壳接口，拉取就只有 `ExtSync` 一条路径 |
| 不破坏现有链路 | 新的 SQLite 库 `otsmail_ext.db`、独立的 `/ext/*` 路由、独立的 D1 表；`email` 表、`MailCache`、推送代码一行未改 |

只拉 `INBOX`。已发送 / 草稿 / 自定义文件夹留到后续批次。

## 2. 本地表结构（SQLite `otsmail_ext.db`，DB_VERSION = 1）

独立数据库文件，与 `otsmail_cache.db` 完全隔离；升级只动这个库。

### 2.1 `ext_state`（每账户一条拉取游标）

```sql
CREATE TABLE IF NOT EXISTS ext_state (
  ext_id        INTEGER PRIMARY KEY,              -- 与 /ext/accounts 的 ext_id 一致
  address       TEXT    NOT NULL DEFAULT '',      -- 冗余一份地址，便于诊断
  uid_validity  INTEGER NOT NULL DEFAULT 0,       -- 上次成功同步时的 UIDVALIDITY
  last_uid      INTEGER NOT NULL DEFAULT 0,       -- 已处理到的最大 UID
  uid_next      INTEGER NOT NULL DEFAULT 0,       -- 上次登录时服务器报的 UIDNEXT（诊断用）
  last_sync_at  INTEGER NOT NULL DEFAULT 0,       -- epoch ms
  last_error    TEXT    NOT NULL DEFAULT ''       -- 失败分类文案，≤300 字
);
```

### 2.2 `ext_mail`（第三方邮件本体）

```sql
CREATE TABLE IF NOT EXISTS ext_mail (
  local_id      INTEGER PRIMARY KEY AUTOINCREMENT,
  ext_id        INTEGER NOT NULL,
  uid           INTEGER NOT NULL DEFAULT 0,
  uid_validity  INTEGER NOT NULL DEFAULT 0,
  message_id    TEXT    NOT NULL,                 -- 无 Message-ID 时用 "uid:<validity>:<uid>" 兜底
  subject       TEXT    NOT NULL DEFAULT '',
  from_name     TEXT    NOT NULL DEFAULT '',
  from_addr     TEXT    NOT NULL DEFAULT '',
  to_name       TEXT    NOT NULL DEFAULT '',
  to_addr       TEXT    NOT NULL DEFAULT '',
  cc            TEXT    NOT NULL DEFAULT '',
  date_ms       INTEGER NOT NULL DEFAULT 0,       -- Date 头缺失时用 INTERNALDATE
  seen          INTEGER NOT NULL DEFAULT 0,       -- IMAP FLAGS 里是否有 \Seen
  snippet       TEXT    NOT NULL DEFAULT '',      -- ≤160 字
  body_text     TEXT    NOT NULL DEFAULT '',
  body_html     TEXT    NOT NULL DEFAULT '',
  att_json      TEXT    NOT NULL DEFAULT '',      -- JSON 数组，只有元信息，不含字节
  archived      INTEGER NOT NULL DEFAULT 0,       -- 服务端归档成功标记
  created_at    INTEGER NOT NULL DEFAULT 0
);
```

索引：

| 索引 | 用途 |
| --- | --- |
| `idx_ext_mail_dedup` UNIQUE `(ext_id, message_id)` | 去重：同一账户同一 Message-ID 只留一行 |
| `idx_ext_mail_list` `(ext_id, date_ms DESC)` | 界面批次按账户倒序列邮件 |
| `idx_ext_mail_uid` `(ext_id, uid)` | 按 UID 反查 / 修正游标 |

写入统一用 `insertWithOnConflict(..., CONFLICT_IGNORE)`，靠唯一索引做幂等。

```sql
CREATE TABLE IF NOT EXISTS ext_mail (

  subject       TEXT    NOT NULL DEFAULT '',
  from_name     TEXT    NOT NULL DEFAULT '',
  from_addr     TEXT    NOT NULL DEFAULT '',
  to_name       TEXT    NOT NULL DEFAULT '',
  to_addr       TEXT    NOT NULL DEFAULT '',
  cc            TEXT    NOT NULL DEFAULT '',

  seen          INTEGER NOT NULL DEFAULT 0,
  snippet       TEXT    NOT NULL DEFAULT '',
  body_text     TEXT    NOT NULL DEFAULT '',
  body_html     TEXT    NOT NULL DEFAULT '',
  att_count     INTEGER NOT NULL DEFAULT 0,

CREATE UNIQUE INDEX idx_ext_mail_dedup   ON ext_mail(ext_id, message_id);

```

### 3.2 `ext_att`（附件元信息 + 对象存储 key）

```sql
CREATE TABLE IF NOT EXISTS ext_att (
  att_id      INTEGER PRIMARY KEY AUTOINCREMENT,
  mail_id     INTEGER NOT NULL,
  user_id     INTEGER NOT NULL,
  ext_id      INTEGER NOT NULL,
  filename    TEXT    NOT NULL DEFAULT '',
  mime_type   TEXT    NOT NULL DEFAULT 'application/octet-stream',
  size        INTEGER NOT NULL DEFAULT 0,
  r2_key      TEXT    NOT NULL DEFAULT '',        -- 空串表示只留元信息、没存字节
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP

CREATE INDEX idx_ext_att_mail ON ext_att(mail_id);
```

### 3.3 `ext_sync_state`

```sql
CREATE TABLE IF NOT EXISTS ext_sync_state (
  ext_id        INTEGER PRIMARY KEY,
  user_id       INTEGER NOT NULL,
  uid_validity  INTEGER NOT NULL DEFAULT 0,
  last_uid      INTEGER NOT NULL DEFAULT 0,
  uid_next      INTEGER NOT NULL DEFAULT 0,
  last_sync_at  DATETIME,
  last_error    TEXT
);
```

表关系：`ext_mail` ← `ext_att`（`mail_id`），`ext_sync_state` 与 `ext_account` 共用 `ext_id`。全部通过 `user_id` 归属隔离，查询一律带 `user_id`。

## 4. 增量游标机制

游标 = `uid_validity` + `last_uid`，客户端与服务端各存一份。

| 场景 | 行为 |
| --- | --- |
| 首次同步（`last_uid = 0`） | `start = max(1, uidNext - limit)`，只取最近 `limit` 封（默认 40），不整箱重拉 |
| 后续同步（`last_uid > 0`） | `start = last_uid + 1`，`UID FETCH start:* (UID)` 只枚举新 UID |
| 每处理一封 | 归档成功 → 本地 upsert → 本地游标推进到该 UID → 循环结束后再写一次 |
| `UIDVALIDITY` 不一致 | 视为邮箱被服务端重建：**本地 `last_uid` 归 0**（保留已落库的旧邮件行），下一封归档把新 `uid_validity` 回写服务端，服务端 `last_uid` 也从头算 |
| 换机 | 本地无游标时用 `/ext/accounts` 返回的 `uid_validity` / `last_uid` 续传，不全量重拉 |
| 服务端 `last_uid` 推进 | `advanceCursor()`：`uid_validity` 相同取 `max(旧, 新)`，不同则直接取新值 |

`limit` 在客户端是参数（`ExtSync.runOnce(context, limit)`），`DEFAULT_LIMIT = 40`。首次同步之外的每轮最多再处理 40 封，避免一轮把几千封全拉完。

边界：服务器不报 `UIDNEXT`（为 0）时 `start` 退化为 1，此时 `listUids` 会枚举全量 UID（只取编号，不下载正文），但本轮处理仍在 `limit` 处截断，不会失控。

## 5. 拉取过程（`ExtImapClient`）

```
连接(20s 超时) → 读问候 → CAPABILITY(取 IDLE 标记) → [163/126 需要时发 ID]
→ LOGIN "地址" "授权码" → EXAMINE INBOX（只读，不动已读标记）
→ UID FETCH <start>:* (UID)  → 逐封 UID FETCH <uid> (UID FLAGS INTERNALDATE BODY.PEEK[])
→ LOGOUT
```

- `EXAMINE` 而非 `SELECT`：只读会话，不会把未读变已读。
- `BODY.PEEK[]`：同样避免隐式置 `\Seen`；`\Seen` 只从 `FLAGS` 里读出来存库。
- 正文按 literal `{n}` **字节级**读取（不按行读，避免 base64 换行破坏内容）。
- 读超时 90s；单封失败向上抛，本轮该账户中止，游标停在上一封。
- 失败分类复用第一批枚举：连不上 / 超时 / TLS 失败 / 认证失败 / 未开 IMAP / 未知。

## 6. 解析策略（`MimeParser`）

口径：整封原文按 ISO-8859-1 转成 1:1 字节视图先做**结构切分**（头部、boundary、literal），解码只发生在需要输出字符串的位置。

| 项 | 处理 |
| --- | --- |
| 结构 | `multipart/*` 递归（深度上限 6），`message/rfc822` 只登记 `.eml` 元信息，不展开 |
| 正文 | 取第一个 `text/plain` 与第一个 `text/html`；都没有时用其它 `text/*` 兜底 |
| 传输编码 | `base64`（`Base64.getMimeDecoder`，容忍换行）、`quoted-printable`（含 `=\r\n` 软换行与 `=XX`）、其它原样 |
| 头编码 | RFC 2047 `=?charset?B/Q?...?=` 循环解码；相邻编码词的空白按规范丢弃；未编码 8-bit 头按 UTF-8 → GB18030 救回 |
| 字符集回退链 | 首选（`gb2312/gbk/gb18030/x-gbk/cp936` 统一映射到 GB18030）→ GB18030 → UTF-8 → ISO-8859-1，全部严格解码，失败才降级 |
| 附件名 | `filename*` 优先（RFC 2231，`charset'lang'percent-encoded`），否则 `filename`，否则 `name`；无文件名但 `Content-Disposition: attachment` 时给默认名 |
| 地址 | `Name <addr>` 与裸地址都支持；显示名走头部解码；逗号拆分时引号内的逗号不拆 |
| 日期 | `Date` 头 6 种常见格式（`Locale.US`，按 GMT 解析）；缺失用 `INTERNALDATE` |
| Message-ID | 原样保留 `<...>`；为空时客户端用 `uid:<uidValidity>:<uid>` 兜底，保证去重键始终存在 |
| 摘要 | `snippet()`：优先纯文本；只有 HTML 时去标签并压缩空白，截 160 字 |

附件体积：单附件超过 **5 MB 只保留元信息**（`data = null`），不再持有字节；单封合计与数量上限在服务端再收一次。

## 7. 上传归档与 R2 策略

`POST /ext/mail/archive`，请求体：`extId / uid / uidValidity / date / seen / subject / fromName / fromAddr / toName / toAddr / cc / messageId / snippet / text / html / attachments[]`（附件元素 `filename / mime / size / dataB64`）。

服务端行为：

1. 校验 `ext_id` 归属（`user_id + is_del = 0`），`messageId` 必填。
2. 截断：`subject` 512、`from/to` 姓名 200 / 地址 320、`cc` 640、`snippet` 200、`body_text` 与 `body_html` 各 **256 KB**。
3. 附件上限：**单附件 5 MB、单封合计 15 MB、最多 12 个**；超出的只写元信息（`r2_key = ''`、`size` 保留）。
4. 幂等：`(ext_id, message_id)` 已存在则**不写库、不重复上传附件**，但仍推进游标（避免重复邮件卡住游标）。
5. 附件落对象存储：`r2Service.putObj`（R2 / S3 / KV 自适应），key = `ext/<userId>/<extId>/<hash16>/<序号>-<安全文件名>`；`hash16 = SHA-256(extId:messageId)` 前 8 字节。
6. 附件存失败不影响邮件本体：该条 `r2_key` 置空，元信息照存。
7. 最后 `advanceCursor()` 推进服务端游标。

**体积上限与清理策略**：

- 单封上限 15 MB 是 Worker 请求体与 D1 单行实际可用的保守值；256 KB 正文上限防止单封 HTML 撑爆 D1 行。
- 归档正文在 D1，附件字节在 R2。R2 按量计费，附件保留策略为**随账户生命周期保留**。
- `POST /ext/accounts/delete` 先 `dropArchive()`：删该 `ext_id` 全部 `r2_key` 对象 → 删 `ext_att` → 删 `ext_mail` → 删 `ext_sync_state`，再软删 `ext_account`。对象删除失败不阻断解绑。
- 目前没有「按时间自动清理旧邮件」的后台任务（Workers 免费额度下不做 Cron）；后续如需保留窗口，按 `date` 做批量删除即可。

## 8. 容错与去重

| 场景 | 行为 |
| --- | --- |
| 单账户失败 | 捕获后只停该账户：本地 `markError` + `POST /ext/mail/sync-error`，其余账户继续 |
| 失败原因可诊断 | 客户端映射成中文分类（连不上 / 超时 / TLS / 认证失败 / 没开 IMAP / 拉取失败）+ 服务器回显前 180 字；服务端 `last_error` ≤300 字，`/ext/accounts` 的 `sync_error` 可读 |
| 网络中断 | 每封「归档 → 落库 → 推进游标」提交，中断只丢当前这一封；下次从 `last_uid + 1` 续，不重拉前面的 |
| 重复入库 | 双保险：本地 UNIQUE `(ext_id, message_id)` + 服务端 UNIQUE `(ext_id, message_id)` |
| 口令失效 | `ExtImapException(AUTH_FAILED)` → 账户级失败，其他账户不受影响 |
| 触发节流 | `ExtSync.maybeSync`：SharedPreferences 15 分钟节流 + `AtomicBoolean` 防重入 + `SupervisorJob` on `Dispatchers.IO` |
| Demo 构建 | `BuildConfig.DEMO` 直接跳过；无 token / 无 base 也跳过 |

口令链路：拉取前 `POST /ext/accounts/credential` 单次解密下发明文（AES-256-GCM，AAD=`userId:accountId:provider`），客户端**只在内存持有**，连接关闭即释放；不落盘、不进日志、不写 SharedPreferences。

## 9. 真实可跑 / 占位

**真实可跑（本批已接通）**

- 绑定后进入收件箱即静默触发拉取：取口令 → IMAP 只读登录 → 按游标增量取 UID → 逐封解析 → 归档 → 本地落库 → 推进游标。
- MIME 解析覆盖 GBK/GB18030、base64、quoted-printable、RFC 2047、RFC 2231；7 条单测覆盖。
- 本地 `otsmail_ext.db` 写入与去重；服务端 D1 `ext_mail` / `ext_att` / `ext_sync_state` 与 R2 附件上传。
- `UIDVALIDITY` 变化重置、单账户隔离、失败原因回写（本地 + 服务端）。
- 解绑时清空归档与附件对象。

**占位 / 本批未做（按约定留到后续批次）**

| 项 | 现状 |
| --- | --- |
| 无界面 | 拉到的邮件只在本地库和服务端归档里，App 里看不到；没有统一收件箱、没有按账户筛选 |
| 无推送 | 没有任何后台触发或常驻任务；只在「进入收件箱 + 超过 15 分钟」时跑一轮 |
| 无通知去重 | 未按 Message-ID 做本地通知去重 |
| 无 OAuth | Gmail / Outlook 仍走应用专用密码或授权码，没有 OAuth 2.0 |
| 本地不存附件字节 | `att_json` 只有元信息；附件字节只在服务端对象存储（界面批次再定下载策略） |
| `ExtMailStore.deleteAccount` 未接 UI | 方法已实现但本批无调用点（服务端解绑接口已清归档） |
| 服务端不复核探测 | `/ext/bind` 仍信任客户端回传的 `imapOk/smtpOk` |
| 只拉 INBOX | 已发送 / 草稿 / 自定义文件夹未覆盖 |
| 单轮上限内不重试 | 同一轮内遇到瞬时断网就中止该账户，靠下一轮从游标继续，没有轮内退避重试 |
| 无保留期清理任务 | 附件随账户保留，没有按时间的自动清理 |
