# 聚合收件箱（Gmail / Outlook / 163 / QQ）技术可行性与方案

> 核实日期：2026-11-06
> 范围：只做事实核实与方案取舍，不含业务代码。
> 标注约定：**【已验证】**＝官方文档可查（附链接与文档日期）；**【第三方】**＝非官方来源，仅作线索；**【待实测】**＝文档未覆盖，必须跑一次才知道。

---

## 0. 结论先行

1. **`cloudflare:sockets` 的 `connect()` 没有公开的端口白名单，唯一文档明确封禁的是 25（SMTP）。** 993 / 465 / 587 在语法和文档层面都不被禁止（官方示例直接连 5432），但**"能连"不等于"能常驻"**——Workers 的 socket 生命周期绑在单次请求上，且不能在全局作用域建连，IMAP IDLE 这种"挂 29 分钟等服务器推 EXISTS"的模式在 Workers 里做不了。
2. **真正能长期跑 IMAP IDLE 的是 Cloudflare Containers**：2026-04-13 已 GA，Workers Paid（$5/月）即可用；非 80/443 的出站流量（含 993）在 `enableInternet = true` 时直连、不经过 outbound 拦截。但平台**不保证实例常驻**：默认 10 分钟无请求就 sleep，宿主机维护会 SIGTERM（15 分钟宽限），必须自己写重连与守护。
3. **"秒级"这个硬指标，四家里只有转发和 IMAP IDLE 能稳定做到；Gmail 的 `users.watch`+Pub/Sub 可以做到秒级；Outlook 的 Graph 订阅官方给的是"通常 <1 分钟、最坏 3 分钟"，不满足"不要几十秒延迟"的字面要求。**
4. **纯转发是最便宜、覆盖最全、上线最快的路，但它是单向只读**：拿不到已读/删除/文件夹状态，拿不到历史邮件，也不能代发。要做"三星邮件客户端那种聚合"，转发只能当**通知层**，不能当数据层。
5. **推荐路线：双轨但分阶段** —— 先用转发打通四家的秒级通知与统一收件（成本≈0，1～2 周可上线）；再用 Gmail API / Graph 补齐 Gmail、Outlook 的双向能力；163 / QQ 因为没有任何官方推送接口，只能靠容器里的 IMAP IDLE，放到最后按账号数按需扩容。
6. **最大的两个非技术风险**：Gmail 的 `gmail.readonly` 属 restricted scope，公开分发要过 CASA 安全评估（未过之前测试态上限约 100 用户）；FCM 在无 GMS 的国产 ROM 上拿不到 token，现有客户端代码已经承认这一点（见 [PushManager.kt](file:///e:/DeepSeek%20workers/otsmail-android/app/src/main/java/com/otscup/otsmail/data/PushManager.kt#L37-L38)），而 163/QQ 用户恰恰大概率在这类机器上。

## 1. 决定性事实核实

### 1.1 Workers 出站 TCP 端口（最关键一条）

**【已验证】** 官方文档《TCP sockets》，最后更新 2026-10-13：
<https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/>

文档里与端口相关的只有三条硬信息：

- **只禁止 25 端口**："By default, Workers cannot create outbound TCP connections on port `25` to send email to SMTP mail servers."（Troubleshooting 章节还有专门的 `Connections to port 25 are prohibited` 条目）。
- **没有允许端口清单**。`SocketAddress` 的 `port` 说明给的示例是 `5432`（Postgres）；Workers VPC 的文档同样用 `connect()` 连 6379（Redis）。也就是说 993 / 465 / 587 在文档层面**不是被封禁对象**。
- **但要命的运行时约束在 Considerations 一节**：
  - "TCP sockets cannot be created in global scope and shared across requests. You should always create TCP sockets within a handler."
  - "Each open TCP socket counts towards the maximum number of open connections"（Workers 限制为**同时 6 个处于"等响应头"阶段的连接**，见 <https://developers.cloudflare.com/workers/platform/limits/#simultaneous-open-connections>）。
  - 在 Durable Object 里开的 socket 最多只能把 DO 保活 **15 分钟**，"After 15 minutes, the socket stops keeping the Durable Object alive"。

**推论（工程判断，非文档原文）**：

| 目标 | 能否在 Workers 做 | 依据 |
| --- | --- | --- |
| 993 建连 + 登录 + 选箱 + 拉一批 header（单次请求内完成，秒级） | **理论可以，【待实测】** | 文档无禁止 + 示例用 5432；但无 993 的官方用例，且平台可能另有未公开策略 |
| 465/587 建连 + 发一封信（单次请求内完成） | **理论可以，【待实测】** | 同上；25 明确禁，465/587 未提 |
| IMAP IDLE 常驻（挂起等新邮件） | **不行** | socket 不能跨请求复用；DO 保活上限 15 分钟 < IDLE 常见 29 分钟刷新周期 |

**【已验证】** 另一个容易忽略的事实：Workers 的 TCP 出站源 IP 来自**不在 Cloudflare 公布 IP 段里**的独立前缀（同一文档："TCP Workers outbound connections are sourced from a prefix that is not part of list of IP ranges"）。这意味着邮箱服务商看到的是一批"陌生的云 IP"，对反滥用策略、信誉评分都是负面信号，163/QQ 尤其需要实测。

**间接方案有没有？**

- **Hyperdrive**：只解决 Postgres 连接池，对 IMAP 无用。
- **Workers VPC**：2026-06-16 起 `connect()` 可走 VPC Network binding 连私有网段（<https://developers.cloudflare.com/changelog/post/2026-06-16-tcp-connect-vpc-networks/>），但那是"连你自己的私有网络"，不是"替你去连公网 993"。
- **Service binding 的 `connect()` handler**：可以让一个 Worker 接收另一个 Worker 转发的入站 TCP，但文档写明"Support for handling inbound TCP connections from other sources is coming soon"，且这是入站方向。
- **结论：没有绕过"常驻"限制的 Workers 方案，要常驻只能上 Containers。**

### 1.2 Cloudflare Containers 现状

**【已验证】** 已 GA：Containers Changelog "Containers and Sandboxes are now generally available"，2026-04-13
<https://developers.cloudflare.com/changelog/post/2026-04-13-containers-sandbox-ga/>
文档首页标注 "Available on Workers Paid plan"（<https://developers.cloudflare.com/containers/>，更新 2026-10-12）。

**出站能力**（《Handle outbound traffic》，更新 2026-10-29）：
<https://developers.cloudflare.com/containers/configuration/outbound-traffic/>

- `enableInternet = false` 时"Only ports 80 and 443 are available"（外加 DNS），其它端口一律拒绝。
- **非 80/443 的流量本来就不经过 outbound handler**："Traffic on ports other than 80 and 443 is never routed through outbound or outboundByHost"。
- 反过来读：`enableInternet = true` 时，**993 这类非 HTTP 端口是直连出网的**，不受 `deniedHosts` 约束（原文："While enableInternet is true, connections to other ports bypass deniedHosts"）。
- 465/587 同理可直连。**25 端口没有查到 Containers 侧的明文封禁文档**，按平台一致策略应按"被封"处理，方案里只使用 465/587。

**生命周期**（FAQ + Lifecycle，更新 2026-10-05 / 2026-09-30）：
<https://developers.cloudflare.com/containers/faq/>、<https://developers.cloudflare.com/containers/concepts/architecture/>

- 默认 `sleepAfter = 10 分钟`，无请求即 `stop()`；可以改长，但**平台明确不保证实例运行时长**："Cloudflare does not guarantee that any container instance will run for a set period."；宿主机重启等事件会 SIGTERM → 最多等 15 分钟 → SIGKILL，之后由流量触发在新机器上起新实例。
- 磁盘默认临时（重启即回到镜像状态），要持久化得用 snapshot 或 FUSE 挂 R2。
- **对 IMAP IDLE 的含义**：不能假设"部署一次就永久在线"。要写：断线重连、SIGTERM 优雅退出、由 Durable Object alarm 定时唤醒/健康检查、按 Message-ID 幂等去重（因为重连后可能重复拉到同一封）。

**计费**（《Pricing》，更新 2026-04-21）：
<https://developers.cloudflare.com/containers/pricing/>
单价：内存 \$0.0000025/GiB-秒（含 25 GiB-小时/月）、CPU \$0.000020/vCPU-秒（含 375 vCPU-分钟/月）、磁盘 \$0.00000007/GB-秒（含 200 GB-小时/月）。**只在实例运行期间计费，sleep 即停费**。

按 30 天 = 2,592,000 秒、24 小时常驻估算（IMAP IDLE 基本不吃 CPU，按 2% 占用折算）：

| 实例规格 | 内存 | 磁盘 | 内存费 | 磁盘费 | CPU 费 | 合计/月（不含 $5 套餐） |
| --- | --- | --- | --- | --- | --- | --- |
| lite（1/16 vCPU / 256 MiB / 2 GB） | 0.25 GiB | 2 GB | 648,000 GiB-s，超出 558,000 → **\$1.40** | 5,184,000 GB-s，超出 4,464,000 → **\$0.31** | 约 3,240 vCPU-s，在额度内 → **\$0** | **≈ \$1.7/实例/月** |

| standard-1（1/2 vCPU / 4 GiB / 8 GB） | 4 GiB | 8 GB | 超出 10,278,000 → **\$25.70** | 超出 20,016,000 → **\$1.40** | 可能超额度，另计 | **≈ \$27+/实例/月** |

> **一个 lite 实例能承载多少个 IMAP 连接是估算值**：256 MiB 里扣掉运行时基线（约 50～80 MB），每条 IDLE 连接约 1～3 MB，按 **50～80 个账号/实例**做容量假设，**必须压测确认**。

**与 D1/R2/KV 对接**：容器通过其 Durable Object 与 Worker 绑定交互（<https://developers.cloudflare.com/containers/configuration/workers-connections/>）；也可用 FUSE 挂 R2 做持久盘。注意：**不要**把用户凭据打进镜像或落临时盘——镜像对所有实例共享，落盘重启后仍在。

### 1.3 四家邮箱的收信实时性路径

#### Gmail —— `users.watch` + Cloud Pub/Sub

**【已验证】** 《Push Notifications》（文档标注最后更新 2026-09-17）：
<https://developers.google.com/workspace/gmail/api/guides/push?hl=en>

- **前置条件**：Google Cloud 项目 + 一个 Pub/Sub topic；topic 需给 `gmail-api-push@system.gserviceaccount.com` 发布权限；OAuth 授权里要有 `gmail.readonly`（或更强）；`users.watch` 里带 `topicName`。
- **续期**：官方原文 "You must re-call `watch` at least every **7 days** or else you will stop receiving updates for the user. We recommend calling `watch` once per day."；响应里有 `expiration` 字段。→ **必须有一个每日 cron**（Workers Cron Trigger 即可）。
- **配额/速率**：同一用户的通知速率上限 **1 event/秒**；Gmail API 另有每日配额（配额页标注 2026-05-01 起新项目适用新额度：<https://developers.google.com/workspace/gmail/api/reference/quota>）。
- **延迟**：Pub/Sub push 到 HTTPS 端点，实测普遍 1～5 秒级，属于"秒级"可用路径；Workers 侧需验签（Pub/Sub push 的 OIDC JWT 或 shared token）。
- **代价（关键）**：`gmail.readonly` / `gmail.modify` 是 **restricted scope**。公开分发前必须过 Google OAuth 验证 + CASA 安全评估，未过之前停在 Testing 态，**约 100 用户上限**，且每 12 个月复评（<https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification>）。测试态还有一个坑：**Testing 发布状态的 refresh token 7 天过期**（Google OAuth 文档的既有规则），会让"配一次永久用"的体验直接崩掉。
- **绕开 CASA 的办法**：Gmail 仍支持 IMAP + 应用专用密码（需账号开两步验证），走容器路线即可不碰 restricted scope。代价是用户操作步骤多、且 Google 可随时收紧策略（**【待实测】** 当前是否仍对普通 Gmail 账号开放）。

#### Outlook —— Microsoft Graph 变更订阅

**【已验证】** 《subscription resource type》（Graph v1.0）：
<https://learn.microsoft.com/en-us/graph/api/resources/subscription?view=graph-rest-1.0>

- **`message` 资源订阅最长 10,080 分钟（不到 7 天）**；带资源数据的"富通知"更短，1,440 分钟（不到 1 天）。
- 创建订阅时 Graph 会向 `notificationUrl` 发 **validationToken** 校验请求，端点必须**在 10 秒内原样回显**（明文 `text/plain`）；`expirationDateTime` 小于请求后 45 分钟的会被自动抬到 45 分钟。
- **续订**：到期前 `PATCH /subscriptions/{id}` 改 `expirationDateTime`；到期未续则直接失效。
- **权限**：`Mail.Read`（读信）/`Mail.ReadWrite`（改状态）；企业账号需管理员同意，个人 Microsoft 账号走 `common` 端点、用户自 consent 即可。应用需在 Entra 注册，回调域名需 HTTPS。
- **延迟（最要命的一条）**：同一文档的延迟表写明 `message` 的通知延迟"**Less than 1 minute**（典型）/ **3 minutes**（最大）"。→ **Graph 订阅满足不了"不要几十秒延迟"的字面要求**，只能算"准实时"。
- **另一条硬事实**：Outlook.com 自 **2024-09-16** 起停用 Basic Auth，第三方客户端必须 OAuth2/XOAUTH2（<https://support.microsoft.com/en-us/office/outlook-com-no-longer-supports-auth-plain-authentication-07f7d5e9-1697-465f-84d2-4513d4ff0145>）。所以"给用户一个应用密码"这条捷径在 Outlook 上不存在。

#### 163 / QQ —— 有没有官方推送？

**【第三方/查不到官方】** 两家都**没有**面向第三方的邮件 webhook / 推送 API。可查到的官方页面只有"如何用第三方客户端（POP/IMAP/SMTP）配置"，没有任何 push 订阅文档。

- **IMAP IDLE**：官方文档均未声明支持。第三方线索互相矛盾——有 2019 年的实测文章称"网易 163 免费邮箱不提供 IDLE"，但也有 2026 年的开源客户端把 163 归入"IMAP IDLE 可用"，并提到"QQ / Foxmail 的 IDLE 通知不可靠、需要主动补查"。→ **【待实测】**，判据就是 `CAPABILITY` 里有没有 `IDLE`，以及挂 IDLE 后新邮件到达的实际时延。
- **163 的额外坑【第三方】**：`imap.163.com` 会拒绝不发 `ID` 命令（不自报客户端名）的连接，直接回 `Unsafe Login`。这是硬编码级别的兼容要求，容器里必须实现。
- **授权码**：
  - QQ：官方明确为 **16 位授权码**，需短信验证后生成，用于 POP/IMAP/SMTP（<https://help.mail.qq.com/detail/0/1088>、<https://help.mail.qq.com/detail/106/985>）。
  - 163：Webmail → 设置 → 客户端授权码 开启；企业版官方称"最多 20 个授权码"（<http://www.163.gd.cn/help/safe/safe_166.html>）。**个人免费邮箱的授权码上限查不到官方页**，社区反馈是"免费 2 个、要更多得开会员"（V2EX 帖 <https://staging.v2ex.com/t/1123615>，非官方）。**【待实测】**。
- **并发连接数限制**：**两家都没有公开文档**。行业经验值通常是每账号 5～10 条 IMAP 连接，超出会被拒或限速。**【待实测】**：单账号开 1 条 IDLE + 1 条按需 FETCH 是最稳的做法，不要多开。
- **对境外/云厂商出口 IP 的限制**：**查不到官方文档**。已知间接证据是 QQ 官方对"发信 IP 频率"有阶梯封禁（见 1.5），收信侧是否按 IP 段风控没有公开说明。Cloudflare 的 TCP 出口又是独立前缀（1.1），**必须实测**：连续 24 小时挂 IDLE 是否被断、是否触发"异地登录"提醒。

### 1.4 自动转发作为替代路径

| 提供商 | 能否转发到外部地址 | 前置条件 | 是否丢原发件人身份 | 已知限制 | 状态 |
| --- | --- | --- | --- | --- | --- |
| Gmail | 能 | 在"转发和 POP/IMAP"里添加目标地址，**目标邮箱要点确认链接/验证码** | **保留原 From**（转发不是"重新发送"） | 免费；转发后 SPF 通常不过（见 1.6） | 【第三方，操作路径一致】官方帮助未直接取到 |
| Outlook.com | 能 | 设置 → 邮件 → 转发和 IMAP → 启用转发 | **会变成"从你的账号转发"**：官方明确"replies to those messages will automatically be addressed to your account, and not to the original sender" | 回复链路被打断 | 【已验证】<https://support.microsoft.com/en-us/outlook/turn-on-or-off-automatic-forwarding-in-outlook-com> |
| QQ | 能（走"收信规则"里的转发动作） | **目标邮箱需先验证转发功能**，规则才启用 | 一般保留原 From | 同一目标多条规则只有较新的一条生效 | 【已验证】<https://help.mail.qq.com/detail/0/1027> |
| 163 | 能 | 设置里开启自动转发 | 一般保留原 From | **免费邮箱 1 个转发地址、收费 2 个**；**只转发收件箱**，垃圾箱/订阅箱/来信分类命中的邮件不转发 | 【第三方，网易 VIP 帮助页 <https://help.vip.163.com/faqDetail.do?code=d7a5dc8471cd0c0e8b4b8f4f8e49998b374173cfe9171305fa1ce630d7f67ac2163a1e89710f524f>，免费版需再核】 |

**验证码类邮件有没有例外**：四家都**没有公开说明**会拦截验证码转发。QQ 的"收信规则"可以按条件筛选，反而可能把验证码邮件漏掉（规则写错就全漏）。→ **【待实测】**：用真实验证码邮件跑一轮四家转发。

**对现有架构的直接冲击（代码事实）**：转发会破坏 SPF（部分破坏 DMARC），而现有收信管线会把结果落库到 `email.auth_spf` / `email.auth_dmarc`（见 [init.js](file:///e:/DeepSeek%20workers/otsmail/mail-worker/src/init/init.js#L881-L897)），下游规则/分类可能把这些邮件判成可疑。**转发来源必须打可信标记**（例如只接受来自自家 Email Routing 的入站、校验信封收件人命中预留别名），否则等于给自己开一个伪造入口。

**规模上限（已验证）**：Cloudflare Email Routing 每域名 **200 条路由规则**、每账号 **200 个已验证目标地址**、入站邮件 **25 MiB**（<https://developers.cloudflare.com/email-service/platform/limits/>）。但聚合场景是**入站**：用 **catch-all → Email Worker** 接全部 `别名@你的域`，不消耗"200 条规则"；200 个"目标地址"限制针对的是出站转发目的地，不是入站别名。→ 入站别名可以做到"每账号一个"，不受 200 限制。

### 1.5 SMTP 代发的现实约束

| 提供商 | 第三方客户端能否以授权码/令牌发信 | 端口 | 每日限额（官方口径） | 云 IP 被判垃圾邮件的已知情况 |
| --- | --- | --- | --- | --- |
| Gmail | 能：SMTP + 应用专用密码，或 XOAUTH2 | 465 / 587 | **个人 500 封/天，Workspace 2000 封/天；单封最多 100 个收件人**（<https://developers.google.com/workspace/gmail/imap/imap-smtp>） | 无官方说明；Cloudflare 出口是陌生前缀，信誉未知 |
| Outlook.com | **只能 OAuth2**（Basic Auth 已于 2024-09-16 停用） | 587（STARTTLS） | Microsoft 365 订阅者 5,000 收件人/天、单封 500；**非订阅者更低且会按使用历史动态调整**（<https://support.microsoft.com/en-us/outlook/sending-limits-in-outlook-com>） | 无官方说明 |
| 163 | 能（授权码） | 465 / 994 类 SSL | **普通用户 300～400 封/天；会员 700～1400**（<https://help.mail.163.com/faqDetail.do?code=d7a5dc8471cd0c0e8b4b8f4f8e49998b374173cfe9171305fa1ce630d7f67ac27ae9194e21b954ec>） | 无官方说明 |
| QQ | 能（16 位授权码） | 465 / 587 | **没有公布"每账号每日封数"**，但有按 IP/域名的阶梯封禁：分钟→小时→当日（<https://help.mail.qq.com/detail/0/1073>） | **有官方机制**：同 IP 发信频率超限即 550 拒收 |

**三条工程结论**：

1. **Gmail SMTP 发信不会自动进"已发送"**：走 SMTP 时服务器只负责投递，要归档必须客户端自己 `APPEND` 到 `[Gmail]/Sent Mail`（Gmail 专属文件夹名还是本地化的）。用 Gmail API `messages.send` 可以顺带落到 SENT。
2. **从 Cloudflare 出口代发，SPF 由提供商签（信封域是他们的），但 `Received` 链里会出现 Cloudflare 的陌生 IP**，反垃圾打分不可控；QQ 更是直接按 IP 频率封。→ **代发要限流 + 失败可见 + 不承诺送达**。
3. **Cloudflare 自己的发信绑定不能替代**：`send_email` binding 只能发给"已验证的目标地址"（<https://developers.cloudflare.com/email-routing/email-workers/send-email-workers/>），不能给任意收件人发信；新出的 Email Service 是"从你的域发"，也改不了"以用户原邮箱身份发"这件事。

## 2. 三条候选路线对比

### 路线 A：纯转发（Forwarding only）

| 维度 | 值 |
| --- | --- |
| 做法 | 引导用户在四家后台开启"自动转发"→ 转发到 `别名@你的域` → Email Routing catch-all → 现有 Worker 收信管线 → D1 `email` → 现有 FCM 秒推 |
| 覆盖 | **四家全支持**（Outlook 会改写成"你的账号转发"，回复链路断） |
| 实时性上限 | **秒级**（邮件到达原邮箱后，转发通常 1～3 秒内完成；不受 Graph 的 3 分钟上限影响） |
| 成本 | **≈0**（Email Routing 免费；只消耗 Worker 调用与 D1 行） |
| 运维复杂度 | **低**（无状态、无常驻进程、无凭据托管） |
| 能力边界 | **单向只读**：没有历史邮件（只能拿到"开启之后"的）、没有已读/删除/文件夹同步、没有发信、不能标记、不能搜索原邮箱 |
| 适合 | 第一版、只想"不漏邮件 + 秒级通知" |

### 路线 B：转发 + SMTP 代发（Forwarding + Send）

| 维度 | 值 |
| --- | --- |
| 做法 | A 的基础上，绑定凭据（Gmail 应用密码 / Outlook OAuth2 / 163·QQ 授权码），发信走各家 SMTP（465/587，Workers 短连接） |
| 覆盖 | 发信四家都能；收信仍是转发 |
| 实时性上限 | 收：秒级（转发）；发：即时 |
| 成本 | 仍≈0（Workers 出站，不占容器） |
| 运维复杂度 | **中**：要托管四套凭据、要处理限流/退信/归档到"已发送"、要处理 Outlook 的 OAuth 刷新 |
| 能力边界 | 仍**没有双向状态同步**：在 App 里读了，原邮箱还是未读；删了，原邮箱还在 |
| 适合 | "能收能发"就够、明确接受状态不同步 |

### 路线 C：常驻容器双轨（Container + IMAP IDLE + 原生 API）

| 维度 | 值 |
| --- | --- |
| 做法 | 每个外部账号一条 IMAP IDLE（163/QQ 必走；Gmail 可用应用密码绕开 CASA；Outlook 用 OAuth2 IMAP），容器检测到 EXISTS 后写 D1 + 调 FCM；Gmail/Outlook 同时挂 `users.watch` / Graph 订阅做冗余；读写状态用 IMAP `STORE`/`COPY` 回写；发信走 SMTP 或原生 API |
| 覆盖 | 四家全部，**能力最接近三星邮件客户端** |
| 实时性上限 | **秒级**（IDLE 是服务器主动推 `EXISTS`）；Gmail 订阅同秒级；Outlook Graph 仍受"典型<1 分钟"限制，但 IMAP IDLE 能盖过它 |
| 成本 | \$5 Workers Paid + **约 \$1.7/月（lite 常驻）～ \$6.9/月（basic）每实例**；50～80 账号/实例（估算，需压测）；另有 DO duration、egress、日志费 |
| 运维复杂度 | **高**：断线重连、SIGTERM 优雅退出、幂等去重、每账号连接配额、凭据在内存中、容器滚动更新、告警 |
| 能力边界 | 受各家 IMAP 实现差异折磨（163 要发 `ID`、文件夹命名本地化、UTF-7 编码、Gmail 标签语义近似文件夹） |
| 适合 | 认真做"聚合客户端"，愿意为此付月费与运维 |

### 一句话取舍

- **要快上线、只要不漏信** → A。
- **要能回信、不介意状态不同步** → B。
- **要像三星客户端那样"一个收件箱管四个号、已读删除都同步"** → C，且必须接受"容器不是真常驻、要自己写守护"。

> 补充一个介于 B 与 C 之间的变体（**B+：转发 + 按需 IMAP 短连接**）：通知靠转发拿秒级，打开列表/详情/改状态时用 Workers 的 `connect()` 现场连 993 拉取。省掉容器成本，但**依赖 1.1 的 993 【待实测】**，且首屏会有一次 200～800 ms 的握手延迟，批量操作受 6 连接限制。若 993 实测可通，这是性价比最高的双向方案。

## 3. 建议的分阶段落地顺序

| 阶段 | 内容 | 难度 | 前置依赖 | 验收标准 |
| --- | --- | --- | --- | --- |
| **P0 地基（1～2 周）** | 外部账号模型 + 每账号唯一入站别名 + catch-all 路由 + 转发接入向导（四家图文步骤）+ 统一收件箱已读态 = 本地态 | 低 | Email Routing catch-all → Worker；D1 新表；现有 `account/email` 表复用 | 四家各发一封，30 秒内到 App；`allReceive=1` 列表能看到；不污染各账号本地已读 |

## 4. 第三方凭据的存储与泄露风险

### 4.1 凭据清单与爆炸半径

| 凭据 | 有效期/刷新 | 一旦泄露能做什么 | 用户侧可撤销 |
| --- | --- | --- | --- |
| Gmail refresh token（`gmail.readonly`/`modify`） | 长期；**Testing 态 7 天过期**，发布态长期 | **读全量邮件 + 改状态**（`gmail.modify` 还能删） | Google 账号"第三方应用"页移除 |
| Gmail 应用专用密码 | 直到用户撤销 | 完整 IMAP/SMTP，等同邮箱权限 | Google 账号页撤销 |
| Microsoft refresh token（`Mail.Read`/`Mail.ReadWrite`） | 约 90 天滑动（个人账号），需持续使用保活 | 读/改/发 | Entra "我的应用"移除 |
| 163 授权码 | 长期，除非用户删除 | 完整 IMAP/SMTP | 只能登录网页版删除；**免费版名额少（待实测）** |
| QQ 16 位授权码 | 长期 | 完整 IMAP/SMTP | 网页版"账户"里删除 |

> 结论：这四类凭据**都不是"只读通知"级别**，而是"邮箱全权"。泄露一次 = 该用户全部历史邮件与发信能力。因此**不能像 `push_device.token` 那样明文存 D1**。

### 4.2 存储方案（建议）

- **加密落库**：`ext_account.secret_cipher` 存 AES-256-GCM 密文，AAD 绑定 `user_id + account_id + provider`；主密钥只放 Worker secret（`CRED_KEY`），支持 `secret_version` 做轮换。
- **绝不下发客户端**：客户端只拿账号元信息（provider / 邮箱 / 状态 / 上次同步时间）；所有拉取在服务端完成——这样"换机同步"只需登录一次。
- **不落日志**：现有代码里 `fcm-service.js` 会打 `token=…${token.slice(-8)}` 这类尾号（[fcm-service.js](file:///e:/DeepSeek%20workers/otsmail/mail-worker/src/service/fcm-service.js#L169-L181)）；凭据必须比这更严——**只允许打 provider + 状态码**。
- **容器侧**：凭据经 DO props 注入内存，**不写文件、不进镜像**（镜像全实例共享，落盘等于全量泄露）；容器重启后由 DO 重新注入。
- **D1 部署面**：D1 对 Cloudflare 运维方是明文可见的，加密只解决"库被拖走/误导出"这一类风险；如果要抵御平台侧，只能自持 KMS 或端到端加密，成本另计（**本轮不建议**）。
- **生命周期**：解绑 = 删除密文 + 调撤销接口（Gmail `token/revoke`、Graph 删订阅、163/QQ 只能提示用户手动删）；90 天未活跃自动降级为"仅转发"并清除凭据。

### 4.3 其它泄露面

- **Pub/Sub / Graph 回调端点**必须验签（Pub/Sub 的 OIDC JWT、Graph 的 `clientState`），否则任何人可以伪造"有新邮件"触发推送风暴。
- **转发别名**是可猜测的入口：`别名@域` 一旦被猜到，攻击者可以往你库里灌垃圾邮件。→ 别名用不可枚举的随机串，且只接受 `Email Routing` 内部入站（校验 `Authentication-Results`/信封来源）。
- **审计**：绑定、解绑、token 刷新失败、连续 401 都要留痕（现有 `security/security.js` 体系可复用）。

## 5. 与现有架构的衔接点

### 5.1 通知链路（可原样复用，不改协议）

现有三条并行通道（[email.js](file:///e:/DeepSeek%20workers/otsmail/mail-worker/src/email/email.js#L221-L253)）：

1. `EMAIL_HUB` Durable Object → `/notify`（站内 SSE / WebSocket）；
2. `pushService`（Web Push / VAPID，订阅存 KV）；
3. `fcmService.sendToUser` → data-only 高优先级 FCM（token 存 D1 `push_device`）。

**聚合收件只需要做一件事：让外部邮件也走这三条**。也就是说 P0 阶段把"转发进来的邮件"照现有 `email` 落库后调用同一段 `ctx.waitUntil(...)`，**FCM 的秒级能力不需要任何改造**。P3 容器的 IDLE 检测到新邮件后，也应该走"写 `email` → 调同一个通知函数"，而不是另起一套推送。

> 注意：FCM data-only 消息不带 `notification` 块，通知由客户端本地构建（[OtsMessagingService.kt](file:///e:/DeepSeek%20workers/otsmail-android/app/src/main/java/com/otscup/otsmail/push/OtsMessagingService.kt)）。聚合新账号要复用同一套 payload 字段（`emailId/sender/name/subject/snippet`），客户端只需在标题前加账号标识。

**已知风险**：无 GMS 的国产 ROM 拿不到 FCM token（[PushManager.kt](file:///e:/DeepSeek%20workers/otsmail-android/app/src/main/java/com/otscup/otsmail/data/PushManager.kt#L37-L38) 已把"无 Google 服务"当正常分支处理）。163/QQ 用户与国产 ROM 高度重合，**"秒级"在目标人群上可能先被推送通道打穿**。建议在 P0 就抽 3 台主流国产 ROM 实测到达率；不达标则必须补厂商推送或自建长连接，这是独立于本方案的一条前置风险。

### 5.2 D1 表结构

现有可直接复用的部分：

- `account(account_id, email, user_id, status, latest_email_time, ...)` —— **一个外部邮箱就是一个本地 `account` 行**，`user_id` 指向现有用户；
- `email(email_id, send_email, name, account_id, user_id, subject, content, text, create_time, is_del, ...)` —— 外部邮件按同一张表落库，列表/详情/分类/搜索无需改；
- `push_device` —— 不动；
- `email_count` —— 按 `account_id` 统计，天然支持"每个外部账号一个未读数"。

需要新增（沿用现有 `init.js` 的 `otsmail_NN` 迁移写法）：

```sql
-- 外部邮箱绑定与凭据（与 account 一对一）
CREATE TABLE IF NOT EXISTS ext_account (
  ext_id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,
  account_id INTEGER NOT NULL,          -- 指向本地 account 行（统一收件箱的锚点）
  provider TEXT NOT NULL,               -- gmail | outlook | netease | qq
  address TEXT NOT NULL,
  auth_type TEXT NOT NULL,              -- oauth | app_password | code
  secret_cipher TEXT NOT NULL,          -- AES-256-GCM 密文，永不下发客户端
  secret_version INTEGER NOT NULL DEFAULT 1,
  ingest_mode TEXT NOT NULL,            -- forward | api | imap_idle
  cursor TEXT,                          -- historyId / deltaLink / UIDVALIDITY:UID
  watch_expire_at DATETIME,             -- Gmail watch / Graph subscription 到期
  last_sync_at DATETIME,
  last_error TEXT,
  status INTEGER NOT NULL DEFAULT 0,
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  is_del INTEGER NOT NULL DEFAULT 0
);

-- 转发入站别名（防枚举 + 反查归属）
CREATE TABLE IF NOT EXISTS ingest_alias (
  alias TEXT PRIMARY KEY,               -- 随机串，非邮箱本地部分
  user_id INTEGER NOT NULL,
  account_id INTEGER NOT NULL,
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

`email` 表建议**加列而非建新表**（保持列表/详情零改动）：`source TEXT`（`native|forward|gmail_api|graph|imap`）、`ext_msg_id TEXT`（幂等键：Gmail messageId / Graph internetMessageId / IMAP Message-ID）。现有迁移函数已经是"try ALTER，失败就跳过"的写法（[init.js](file:///e:/DeepSeek%20workers/otsmail/mail-worker/src/init/init.js#L1158-L1164)），照抄即可。

### 5.3 客户端会话模型

- 现在：`Session` 存 `base/token（Keystore 加密）/accountId/email`（[Session.kt](file:///e:/DeepSeek%20workers/otsmail-android/app/src/main/java/com/otscup/otsmail/data/Session.kt#L18-L42)），401 只走 `AuthState.expire()` 不全量登出（[AuthState.kt](file:///e:/DeepSeek%20workers/otsmail-android/app/src/main/java/com/otscup/otsmail/data/AuthState.kt#L12-L24)）。
- 已有多账户能力：`/account/list`、`/account/add`、`/email/list?accountId=0&allReceive=1`（[Api.kt](file:///e:/DeepSeek%20workers/otsmail-android/app/src/main/java/com/otscup/otsmail/data/Api.kt#L373-L390)、[Api.kt](file:///e:/DeepSeek%20workers/otsmail-android/app/src/main/java/com/otscup/otsmail/data/Api.kt#L466-L483)）。
- **结论：客户端不需要新的会话模型**。聚合收件箱 = 在 `account` 列表里多出几行 + 列表行加一个 provider 徽标 + 写邮件时按 `account.accountId` 选发送通道。切换账号仍是"切 `accountId`"，与现在一致。
- **唯一需要新增的交互**：绑定向导（OAuth 用 Custom Tabs，见现有 `OAuthFlow.kt`；163/QQ 走"填授权码"表单）。绑定状态属于服务端，客户端只展示。

## 6. 已验证 vs 待实测（明确清单）

### 已验证事实（可直接写进设计）

1. Workers `connect()` 只明文禁 25 端口，无允许端口白名单（文档 2026-10-13）。
2. Workers socket 不能跨请求/全局复用；DO 内 socket 最多保活 15 分钟；同时 6 个"等响应头"连接。
3. Workers TCP 出口 IP 不在 Cloudflare 公布 IP 段内。
4. Containers 已 GA（2026-04-13），Workers Paid 可用；非 80/443 出站不经过 outbound handler，`enableInternet=true` 时直连。
5. Containers 默认 10 分钟无请求 sleep，平台**不保证运行时长**，SIGTERM 后最多 15 分钟宽限。
6. Containers 计费单价与套餐额度（2026-04 版本），sleep 期间不计费。
7. Gmail `users.watch` 必须 ≤7 天续期（建议每日）、每用户通知上限 1 event/s。
8. Gmail IMAP/SMTP 限额：个人 500 封/天、Workspace 2000、单封 ≤100 收件人。
9. `gmail.readonly` 是 restricted scope，公开分发需 CASA，未过约 100 用户上限、每 12 个月复评。
10. Graph `message` 订阅最长 <7 天；typical <1 分钟、max 3 分钟；validationToken 需 10 秒内回显。
11. Outlook.com Basic Auth 于 2024-09-16 停用。
12. Outlook.com 自动转发会改写为"从你的账号转发"，回复不再回原发件人。
13. 163 每日发信 300～400 封（普通用户）。
14. 163 免费邮箱自动转发仅 1 个地址，且只转发收件箱。
15. QQ 需 16 位授权码（短信验证生成）；收信规则转发需目标邮箱验证后才启用。
16. Cloudflare Email Routing：200 规则/域名、200 目标地址/账号、入站 25 MiB；`send_email` 绑定只能发已验证目标地址。

| H2 | Workers 能连 465/587 完成一次 SMTP 投递 | 同 H1，对四个域名各发一封到自己邮箱 | 失败则代发必须走容器/第三方 |
| H3 | 163 / QQ 的 IMAP `CAPABILITY` 含 `IDLE`，且通知时延 <10 秒 | `CAPABILITY` 直读 + 挂 IDLE 30 分钟打点 | 不支持则 163/QQ 只能靠转发（秒级但单向） |
| H4 | 163 / QQ 对单账号并发连接与 Cloudflare 出口 IP 的容忍度 | 单账号挂 1 IDLE 连续 72 小时，记录断连/重新登录/风控邮件 | 频繁断连则需要多出口或降级为轮询（违背"不要轮询"的前提，需回退产品预期） |
| H5 | 163 个人免费邮箱授权码上限（社区说 2 个） | 真实账号尝试生成第 3 个 | 上限低则用户可能被迫删旧授权码 |
| H6 | 四家转发是否完整保留原 `From`、是否漏发验证码邮件 | 四家各发 10 封（含验证码/带附件/带 SPF+DMARC）对比原始邮件 | 漏验证码则"转发即全局方案"不成立 |
| H7 | 转发流经 Email Routing 后 SPF/DMARC 结果是否被判可疑 | 看 `email.auth_spf/auth_dmarc` 实际落库值 | 被判可疑会污染现有分类/垃圾判定，必须加可信来源标记 |
| H8 | 单实例承载 50～80 个 IDLE 连接的稳定性 | lite 实例压测，观察内存与重连率 | 容量要下调，成本相应上升 |
| H9 | 无 GMS 国产 ROM 的 FCM 到达率 | 3 台机型实测 100 封推送 | 不达标则"秒级"需另建推送通道 |
| H10 | Containers 25 端口封禁与否 | 容器内 `nc -vz smtp.qq.com 25` | 仅影响能否用 25；方案已只用 465/587，影响可控 |

## 7. 不建议做的事（避免过度工程）

- **不要**在 Workers 里硬凑 IMAP IDLE（保活上限 15 分钟，注定不稳）。
- **不要**为"四家统一"去自建 SMTP 中继（Cloudflare 出口 IP 信誉不可控，且 `send_email` 只能发已验证地址）。
- **不要**把 Gmail 走 API 当成唯一路径——CASA 是外部审核长尾，必须有 IMAP+应用密码的兜底。
- **不要**在 P0 就上容器：转发已经能验证"秒级 + 统一收件"这两个产品假设，先证伪再投入。
- **不要**把凭据明文进 D1 或 KV，也不要把凭据下发给客户端（否则"换机同步"会变成"换机泄露"）。
- **不要**承诺 Outlook 的"秒级"：Graph 官方上限就是 3 分钟，IMAP IDLE 才能盖过，而这个结论要等 H3。
